## 二、功能架构总览

```
MQTT收包
  ↓
zk_dispatch_message()
  → sv="plan" 匹配
    → zk_handle_plan_message()
      ├── CT="W" → zk_plan_upsert() → 解析/校验 → Flash双页写入
      └── CT="R" → zk_plan_handle_read()
            ├── DO="nid" → 返回有效计划ID列表
            ├── DO="now" → 返回当前匹配计划(简略版)
            ├── DO="del" + id → 删除单条计划
            └── id=N → 返回单条计划完整内容

主循环每轮:
  zk_work_plan_process()
    → zk_plan_find_current_match()
      遍历 plans[0..7]:
        有效? 已启用? type==1? → 日期范围内? → 星期匹配? → 精确分钟匹配?
      最高优先级获胜
    → zk_apply_plan_brightness()
    → 记录已执行防重入
```

## 三、与协议的差异（仅type=1相关）

### 差异 #1 — 删除命令格式不匹配 【严重 | 平台实际路径】

| 项目 | 协议规定 (7.13) | 代码实现 |
|------|-----------------|---------|
| CT | `"W"` | 代码在 `"R"` 路径下处理 |
| DT格式 | `"del": [1,3,5]` (数组，支持批量) | `"DO": "del"` + `"id": 1` (单条) |

**协议原文** (7.13.2):
```json
{"CT":"W", "DT":{"del":[1,3,5]}}
```

**代码入口** (`zk_work_plan.c:750-795`):
```c
// zk_handle_plan_message
if (strcmp(header->ct, ZK_CT_WRITE) != 0 &&
    strcmp(header->ct, ZK_CT_READ) != 0)
    return BOOL_FALSE;       // CT=D/W之外的都被过滤

if (strcmp(header->ct, ZK_CT_READ) == 0)
    return zk_plan_handle_read(dt, header);  // 删除在这里面

// CT=W 则走到 zk_plan_upsert，解析 plan 对象
```

**数据流**: 平台按协议发 `CT=W, DT.del=[1]` → 进入 `zk_plan_upsert` → 试图解析 `plan` 对象 → 找不到 `id`/`en` 字段 → 返回错误码。

**后果**: ★★★ 平台使用的停用计划功能完全不可用。**这是当前最严重的问题。**

---

### 差异 #2 — "当前运行计划"查询不匹配 【中等】

**查询格式**:

| 项目 | 协议规定 (7.9.2) | 代码实现 |
|------|-----------------|---------|
| 请求 | `"now": cns` | `"DO": "now"` |

**响应格式**:

| 项目 | 协议规定 (7.9.3) | 代码实现 |
|------|-----------------|---------|
| 响应 | 完整plan对象 (含en/id/type/priority/sDate/eDate/week/jobs) | `{id, jobIndex, actionIndex, bri, priority}` 简略字段 |

代码 (`zk_plan_build_now_dt` line 1080-1102):
```c
cJSON_AddNumberToObject(now, "id", match->id);
cJSON_AddNumberToObject(now, "jobIndex", match->job_index);
cJSON_AddNumberToObject(now, "actionIndex", match->action_index);
cJSON_AddNumberToObject(now, "bri", match->bri);
cJSON_AddNumberToObject(now, "priority", match->priority);
```

**后果**: 平台查询当前运行计划会收到错误响应。

---

### 差异 #3 — 回复中缺失类型无关字段 【轻微】

协议7.7.3的查询回应JSON中包含 `setoffset` / `riseoffset` / `dayen` / `onLux` / `onWindow` / `offLux` / `offWindow` 字段。代码的 `zk_plan_record_to_json` 不生成这些字段（它们对type=1无意义）。如果服务器端做严格schema校验会失败。

## 四、已确认的Bug

### Bug #1 — 删除命令无法通过标准协议路径触发 【严重 | 平台实际路径】

即 差异#1。`CT=W + DT.del` 在代码中无处理路径。与现网实际使用方式冲突。

**位置**: `zk_work_plan.c:750-795`，需要新增对 `CT=W` 下 `del` 字段的处理。

---

### Bug #2 — "now"查询命令格式与协议不符 【中等】

即 差异#2。

**位置**: `zk_work_plan.c:1157-1161`

---

### Bug #3 — en=0 禁用时销毁全部数据 【中低 | 平台未使用此路径】

**位置**: `zk_work_plan.c:589-614`, `zk_work_plan.c:724-748`

**根因**: `zk_plan_parse_enabled` 在 `en==0` 时提前 return，但此前已 `memset` 清空结构体。`zk_plan_upsert` 用半空结构体覆盖了 Flash 中的整条记录。

```c
memset(out, 0, sizeof(*out));    // 全部清零
out->valid = 1;
out->id = ...;
out->en = 0;
if (out->en == 0) return 0;      // 提前返回，其它字段全是0

// zk_plan_upsert
next.plans[record.id - 1] = record;  // 覆盖了原有配置
```

**协议依据** (7.4.5): "当en=0时，其他字段可省略" — 意图是"关而不删"，保留配置供后续重新启用。

**现网影响**: 平台走删除来停用计划，不走 en=0，所以当前现网不受此bug影响。但如果未来平台改为 en=0 停用，就会触发。

---

### Bug #4 — 分钟级精确匹配无容错窗口 【低】

**位置**: `zk_work_plan.c:903`

```c
if (action->minute != minute) continue;
```

裸机超级循环中，如果一轮循环因4G AT指令等延迟超过1秒，RTC分钟可能已跳变，导致计划错过触发窗口。因是周期性计划，下一周期会重新匹配，不会永久丢失。

---

### Bug #5 — `data_backup.h` 中备注的Flash地址Z可能重叠

有必要检查 `ZK_PLAN_FLASH_MAIN_ADDR (0x08006000)` 和 `ZK_PLAN_FLASH_BACKUP_ADDR (0x08007800)` 是否与其他模块的Flash区间有冲突。当前地址是硬编码的，需要和 `flash_address_assignment.h` 中的分区规划做交叉确认。

## 五、不合理的设计

### 1. cns_mask (通道选择) 被解析存储但从不在执行中使用

`zk_plan_job_t.cns_mask` 在 JSON 解析和序列化中完整处理，但在 `zk_plan_find_current_match` → `zk_apply_plan_brightness` 中完全被忽略。

当前 `ZK_CNCTRL_SUPPORTED_CNS=1`（单通道设备），所以功能上没问题。但：
- 浪费 1 字节/每条记录，8 字节/每个计划
- 代码读者会困惑
- 如果未来硬件升级到多通道，这里有隐蔽的bug

---

### 2. 每次 `en=0` 或删除都做完整 Flash 双页擦写

仅改一个字段也要擦写两个 1KB Flash 页。STM32F103 Flash 寿命约 10K 次。对低频IoT场景够用，暂时无需优化。

---

### 3. 执行时无任何日志

`zk_work_plan_process` 匹配并执行调光后，没有任何 `printf` 输出。远程排查"计划是否执行了"只能依赖外部观察。

**建议**: 关键节点加日志输出。

---

### 4. 优先级方向有歧义

```c
if (match->found == 0 || plan->priority > match->priority)
```

数值越大优先级越高（8>1）。但协议只定义范围 1~8，没定义方向。如果服务器端认为 1 最高、8 最低，就会产生预期外的计划抢占。

---

### 5. 结构体缺少 packed 属性

混用 `u8`/`u16` 的结构体没有 `__attribute__((packed))`，不同编译器的对齐处理可能不同，Flash二进制布局有跨版本不兼容风险。

## 七、总结

**当前周日期工作计划 (type=1) 的核心链路是正确的**：
- JSON 解析校验完整（与协议错误码对应）
- 双页 Flash 备份 + 魔数/版本/校验保护，存储可靠
- 日期范围 + 星期掩码 + 分钟匹配逻辑正确
- 年循环 (0xFFFF) 跨年区间判断正确
- 防重入执行机制有效

**当前现网最紧急的问题只有一个**：

> ★ **删除命令协议不匹配** — 平台按协议 `CT=W + DT.del=[id]` 下发停用计划，代码不认识。**这是平台停用计划工作流的完全阻断**。

把这个问题修完，周日期工作计划功能对现网就是完整可用的。其它问题按优先级逐步补齐即可。
