# 数字电源项目实施方案

## 1. 目标

基于当前 CAT.1 工程额外创建一个数字电源项目工程，保留 4G 入网、MQTT、中科协议、计划任务、远程控制、运行状态上报等能力，废弃当前 UART2 上的 BL0942 数据采集用途，将 UART2 改为与数字电源通讯。

新工程的核心职责：

- 中科平台下发控制命令后，由 CAT.1 通过 UART2 转发为数字电源协议命令。
- 数字电源返回的电压、电流、功率、温度、故障位，作为平台上报和告警计算的数据来源。
- 单路和双路数字电源使用同一套代码，通过通道配置区分。
- 不再启用原项目中的本地 PWM 调光、本地 ADC 输出采集、BL0942 电参采集作为主业务来源。

## 2. 当前工程依据

### 2.1 当前 UART2 占用

当前工程中 UART2 仍被 BL0942 采集链路占用：

- `Core/Src/main.c` 调用 `hw_uart2_init()`。
- `Core/Src/main.c` 调用 `sys_bl0942_init()`、`sys_bl0942_process()`。
- `Core/Src/sys_tick.c` 调用 `sys_bl0942_timer()`。
- `Core/Src/hw_uart2.c` 当前用于 UART2 底层收发。
- `Core/Src/sys_bl0942.c` 负责交流电压、电流、功率、功率因数、电能计算。

因此数字电源项目中，UART2 的所有权必须从 BL0942 采集切换为数字电源通讯。

### 2.2 当前调光链路

当前中科控制最终会走到：

- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`
  - `zk_apply_brightness(int brightness)`
  - `zk_apply_plan_brightness(int brightness)`
  - 内部调用 `dim_ready()`
- `Core/Src/gateway/net_dim.c`
  - `dim_ready()` 设置 `dim_ready_flag`
- `Core/Src/sys_pwm.c`
  - `sys_pwm_output()`
  - `sys_pwm_process()`
  - 本地 PWM 渐变输出

数字电源项目中，这条链路要改为：

```text
中科 cnCtrl / 计划任务
    -> zk_apply_brightness(cns, brightness)
    -> digital_power_set_brightness(cns, brightness)
    -> UART2 发送 0x3C 数字调光命令
    -> 等待 0x3D 应答
    -> 更新本地通道状态并上报
```

不再通过本地 PWM 输出实现调光。

### 2.3 当前采集和告警来源

当前工程告警不是平台纯计算，也不是传感器直接上报，而是“采样值 + 本地阈值计算”。

主要来源：

- BL0942：`ac_voltage_8209`、`Z_ac_current`、`ac_powerpa`、`ac_pf`、`energy_this_time`。
- 本地 ADC：`Vo_value`、`Io_value`、`Po_value`。
- NTC：`Ntctemp.Ntctemp`。
- 漏电 ADC：`danger_current_warn`、`dangeo_out`。
- 掉电检测：`power_down_flag`，当前主要依赖 `ac_voltage_8209` 判断。

数字电源项目中，平台电参和大部分告警应改由数字电源采样值驱动。

## 3. 数字电源协议确认

### 3.1 基础帧格式

参考单路和双路模拟程序，数字电源协议帧格式为：

```text
帧头    命令   偏移地址   数据长度   数据       校验和   帧尾
0x3A   cmd    offset     len        data...   sum      0x0D 0x0A
```

校验和：

```text
sum = cmd + offset + len + data[0] + ... + data[n-1]
```

### 3.2 单路命令

单路模拟程序发送命令不带通道高位：

| 功能 | 命令 |
| --- | --- |
| 数字调光 | `0x3C` |
| 设置最大电流比例 | `0x31` |
| 查询电参/状态 | `0x3A` |
| 查询型号信息 | `0x35` |

### 3.3 双路命令

双路模拟程序中，部分命令使用命令最高位区分第二路：

```c
cmd = base_cmd + 0x80 * second_out;
```

映射关系：

| 中科通道 | 数字电源通道 | UART2 命令 |
| --- | --- | --- |
| `cns=1` | 第一路 | `base_cmd` |
| `cns=2` | 第二路 | `base_cmd | 0x80` |

接收解析必须先拆通道：

```c
channel = (rx_cmd & 0x80) ? 2 : 1;
base_cmd = rx_cmd & 0x7F;
```

注意：单路模拟程序接收时直接比较 `cmd`；双路模拟程序接收时使用 `cmd & 0x7F`。固件应按双路兼容方式实现，单路自然兼容。

待确认点：

- 双路模拟程序已确认 `0x3C` 调光、`0x31` 最大电流、`0x3A offset=0` 查询全部、`0x35 offset=0x20` 最大电流比例查询会叠加 `0x80 * second_out`。
- 双路模拟程序中的部分单项查询按钮仍发送不带高位的 `0x3A offset=1/3/4`，`0x35 offset=0x0B` 型号查询也不带高位。正式固件不能直接假设所有命令都天然支持 `cmd | 0x80`，需要用实物或电源厂家协议确认“所有 offset 是否都支持通道高位”。
- 第一阶段实现建议仍保留统一的 `digital_power_cmd_with_channel()` 和 `digital_power_channel_from_cmd()`，但对每个命令建立“已验证通道映射表”。未验证命令只允许在单路或 CH1 范围内使用，避免 CH2 查询串路。

### 3.4 UART2 半双工通讯方式

数字电源项目中 UART2 只用于 CAT.1 与数字电源之间的半双工通讯。当前参考代码里的 UART2 非 `_4G_CAT_1` 分支已经体现了半双工思路：

```text
发送前：RS485_TX_ENABLE()
逐字节中断发送：HAL_UART_Transmit_IT()
最后一个字节发送完成：RS485_TX_DISABLE()
接收中断缓存数据：HAL_UART_Receive_IT()
接收间隔超时：RX_FROM_485PORT(rx2_buffer, rx_index)
```

新项目不能继续直接复用 BL0942 的 UART2 业务，但可以复用这个半双工收发模型。需要注意：

- 总线默认处于接收状态。
- 主机 CAT.1 主动发起命令，数字电源只在收到命令后响应。
- 任意时刻只允许一个未完成命令在总线上，不能连续发多条后再统一等响应。
- 发送期间必须关闭或忽略接收缓存，避免把自己发出的数据当成响应。
- 最后一个字节真正发送完成后才能切回接收，不能只在数据写入发送寄存器后就释放总线。
- 切回接收后立即重新启动 `HAL_UART_Receive_IT()`。
- 响应超时、校验错误、长度错误时，本次命令失败，由业务层决定是否重试。

如果硬件是 RS485/485 类收发器，建议保留一个方向控制脚，例如当前工程里的 PA1 方向控制：

```text
TX 方向：DE=1 / RE=1 或对应发送使能
RX 方向：DE=0 / RE=0 或对应接收使能
```

如果硬件确实是 UART 单线连接，不经过 485 收发器，则需要确认 MCU 端是否使用 USART 半双工模式。STM32 可通过半双工配置让 TX 引脚同时承担收发，但实现时仍然要遵守“发送完成后释放线路、再进入接收”的规则。

### 3.5 UART2 初始化要求

数字电源 UART2 初始化建议独立为：

```c
void digital_power_uart2_init(void);
void digital_power_uart2_process_1ms(void);
int digital_power_uart2_send(const uint8_t *buf, uint16_t len);
```

初始化要求：

- 波特率按数字电源实际协议配置。参考单路数字电源工程中 UART2 非 CAT.1 分支使用 `9600`，当前项目 BL0942 分支使用 `4800`，不能沿用 BL0942 波特率。
- 数据格式固定为 `8N1`：8 数据位、无校验、1 停止位。
- 默认进入接收方向。
- 清空接收索引、接收超时计数、发送状态。
- 启动 1 字节接收中断。
- 不在 UART 中断里直接解析完整业务，只负责收字节、发字节和置状态。

建议配置：

```c
huart2.Instance = USART2;
huart2.Init.BaudRate = DIGITAL_POWER_UART2_BAUDRATE;  // 默认 9600，最终以电源协议为准
huart2.Init.WordLength = UART_WORDLENGTH_8B;
huart2.Init.StopBits = UART_STOPBITS_1;
huart2.Init.Parity = UART_PARITY_NONE;
huart2.Init.Mode = UART_MODE_TX_RX;
huart2.Init.HwFlowCtl = UART_HWCONTROL_NONE;
huart2.Init.OverSampling = UART_OVERSAMPLING_16;
```

### 3.6 接收成帧策略

数字电源帧有明确帧头、长度和帧尾，因此建议使用“字节状态机 + 长度判断”，不要只依赖固定延时。

接收状态机：

```text
WAIT_HEADER
    收到 0x3A -> READ_CMD
READ_CMD
    保存 cmd -> READ_OFFSET
READ_OFFSET
    保存 offset -> READ_LEN
READ_LEN
    保存 len，检查 len <= 最大长度 -> READ_DATA
READ_DATA
    收满 len 字节 -> READ_CHECKSUM
READ_CHECKSUM
    保存 checksum -> READ_FOOTER_0D
READ_FOOTER_0D
    必须等于 0x0D -> READ_FOOTER_0A
READ_FOOTER_0A
    必须等于 0x0A -> 校验 checksum -> 生成完整帧事件
```

保留接收间隔超时作为兜底：

- 超过一个完整帧最大时间仍未收完，丢弃当前缓存。
- 收到半帧后超过 `DP_UART2_INTER_BYTE_TIMEOUT_MS` 没有新字节，丢弃当前缓存。
- 完整帧解析后立即清状态，等待下一帧。

建议超时参数：

```c
#define DP_UART2_INTER_BYTE_TIMEOUT_MS   10
#define DP_UART2_RESPONSE_TIMEOUT_MS     200
#define DP_UART2_RETRY_MAX               2
#define DP_UART2_RX_BUF_SIZE             64
#define DP_UART2_TX_BUF_SIZE             64
```

`DP_UART2_RX_BUF_SIZE` 不建议继续沿用 1024 字节大缓存。双路模拟程序的“读 0x3A 全部数据”使用 `len=31`，完整帧长度为 `1 + 1 + 1 + 1 + 31 + 1 + 2 = 38` 字节，因此 64 字节足够覆盖当前聚合帧。不能直接照抄参考 `DTU_protocol.c.txt` 里的 `MAX_DATA_LEN=10`，否则会解析不了聚合返回。

### 3.7 半双工发送状态机

建议 UART2 发送不直接暴露裸发送给业务层，而是由 `digital_power_service` 统一排队，`digital_power_uart2` 只处理底层收发。

底层状态：

```c
typedef enum
{
    DP_UART2_IDLE = 0,
    DP_UART2_TX_ENABLE_WAIT,
    DP_UART2_SENDING,
    DP_UART2_TURNAROUND,
    DP_UART2_WAIT_RESPONSE
} dp_uart2_state_t;
```

发送流程：

```text
1. 确认当前没有等待响应的命令。
2. 清空 RX 缓存和接收状态机。
3. 切换到发送方向。
4. 等待 1 个字符时间或很短保护时间，让方向脚稳定。
5. 启动 HAL_UART_Transmit_IT()。
6. TxCplt 回调确认所有字节已发送。
7. 等待 UART TC 标志，确保最后一个停止位已经发出。
8. 切换到接收方向。
9. 重新启动 HAL_UART_Receive_IT()。
10. 开始响应超时计时。
```

关键要求：

- `RS485_TX_DISABLE()` 必须发生在最后一个字节真实发完之后。
- 如果使用 HAL 的整包中断发送，可以在 `HAL_UART_TxCpltCallback()` 中切回接收。
- 如果使用逐字节发送，最后一个字节回调后还要确认 TC 标志。
- 中断里不要 `printf`，不要做 JSON，不要做 MQTT，不要做复杂业务。
- `digital_power_uart2_send()` 返回忙时，业务层排队或稍后重试，不允许覆盖正在发送的缓冲区。

### 3.8 请求与响应匹配

每条命令发送前，服务层保存一个 pending 请求：

```c
typedef struct
{
    uint8_t active;
    uint8_t cns;
    uint8_t base_cmd;
    uint8_t real_cmd;
    uint8_t offset;
    uint8_t expected_ack_cmd;
    uint32_t start_tick;
    uint8_t retry_count;
} digital_power_pending_t;
```

收到响应后必须匹配：

- `channel` 必须等于 pending 的 `cns`。
- `base_cmd` 必须等于期望应答命令。
- 需要校验 `offset` 的命令，`offset` 必须一致。
- `checksum`、`len`、帧尾必须正确。

命令与期望应答关系：

| 请求 | 请求命令 | 应答命令 |
| --- | --- | --- |
| 设置最大电流比例 | `0x31 / 0xB1` | `0x32 / 0xB2` |
| 查询数据 | `0x3A / 0xBA` | `0x3B / 0xBB` |
| 数字调光 | `0x3C / 0xBC` | `0x3D / 0xBD` |
| 查询型号 | `0x35 / 0xB5` | `0x36 / 0xB6` |
| 设置调光模式 | `0x37 / 0xB7` | `0x38 / 0xB8` |

业务解析时统一先做：

```c
channel = (rx_cmd & 0x80) ? 2 : 1;
base_cmd = rx_cmd & 0x7F;
```

这样单路和双路共用同一套解析逻辑。

## 4. 新工程代码策略

### 4.1 工程组织

建议从当前工程复制出一个新工程目录，例如：

```text
CAT1_DigitalPower_Project/
```

保留当前工程作为原始基线，新工程只服务数字电源版本。

建议增加编译宏：

```c
#define CAT1_DIGITAL_POWER_PROJECT 1
#define DIGITAL_POWER_CHANNEL_MAX 2
#define DIGITAL_POWER_CHANNEL_COUNT 1   // 单路产品配置为 1，双路产品配置为 2
```

如果后续需要同时维护单路/双路烧录包，可以使用两个 Keil Target：

- `DigitalPower_1CH`
- `DigitalPower_2CH`

两者共用源码，只改变 `DIGITAL_POWER_CHANNEL_COUNT`。

### 4.2 新增模块

建议新增以下模块：

```text
Core/Src/digital_power/digital_power_protocol.c
Core/Src/digital_power/digital_power_protocol.h
Core/Src/digital_power/digital_power_uart2.c
Core/Src/digital_power/digital_power_uart2.h

Core/Src/digital_power/digital_power_alarm.h
```

职责划分：

| 模块 | 职责 |
| --- | --- |
| `digital_power_protocol` | 组帧、校验、解析、命令高位通道转换 |
| `digital_power_uart2` | UART2 初始化、收发中断、超时、方向控制 |
| `digital_power_service` | 控制队列、轮询状态机、通道快照 |
| `digital_power_alarm` | 基于数字电源快照生成中科告警状态 |

### 4.3 通道状态结构

建议定义统一快照：

```c
typedef struct
{
    uint8_t online;
    uint8_t brightness;          // 0-100, 平台亮度
    uint8_t power_level;         // 0-200, 数字电源调光值
    uint16_t output_current_ma;
    uint16_t output_voltage_v;
    uint16_t led_power_w;
    uint8_t input_freq_hz;
    uint8_t power_factor_percent;
    uint16_t input_current_ma;
    uint16_t input_voltage_v;
    uint16_t input_power_w;
    uint32_t light_time_h;
    uint64_t energy_wh;
    int16_t internal_temp_c;
    int16_t external_temp_c;
    uint32_t total_runtime_h;
    uint8_t fault_bits;          // bit0 短路, bit1 开路, bit2 限功率
    uint32_t last_rx_tick;
} digital_power_snapshot_t;
```

全局按通道保存：

```c
digital_power_snapshot_t g_dp_snapshot[DIGITAL_POWER_CHANNEL_MAX];
```

### 4.4 控制队列

数字电源半双工总线不允许并发请求，因此所有平台控制、计划控制、周期轮询都必须进入同一个队列。

建议队列项：

```c
typedef enum
{
    DP_REQ_SET_BRIGHTNESS = 0,
    DP_REQ_SET_MAX_CURRENT,
    DP_REQ_QUERY_ALL,
    DP_REQ_QUERY_ITEM,
    DP_REQ_QUERY_MODEL,
    DP_REQ_SET_DIM_MODE,
    DP_REQ_REBOOT
} digital_power_req_type_t;

typedef struct
{
    digital_power_req_type_t type;
    uint8_t cns;       // 1 or 2
    uint8_t offset;
    uint8_t len;
    uint8_t data[8];
    uint8_t retry_max;
    uint32_t enqueue_tick;
} digital_power_request_t;
```

优先级：

```text
平台实时控制 > 计划控制 > 告警确认相关查询 > 周期轮询 > 型号/维护查询
```

处理规则：

- 平台实时调光命令进入队列后，应打断或延后普通轮询。
- 同一通道短时间内连续亮度控制，只保留最后一次亮度，避免总线堆积。
- 周期轮询按通道轮转，双路时不要一直查询一路。
- pending 请求未完成前不发下一条。
- 超时后最多重试 `DP_UART2_RETRY_MAX` 次，仍失败则标记该通道通讯异常。

### 4.5 轮询状态机

单路轮询：

```text
CH1 查询全部/输出电流
CH1 查询输出电压
CH1 查询输入电压
CH1 查询温度
CH1 查询故障位
循环
```

双路轮询：

```text
CH1 查询全部/关键字段
CH2 查询全部/关键字段
CH1 查询温度/故障位
CH2 查询温度/故障位
循环
```

如果数字电源支持 `0x3A offset=0x00 data=31` 这类聚合查询并返回 `0x3B` 聚合帧，优先使用聚合查询；如果实物只支持单项查询，则退回单项轮询。

建议轮询周期：

| 类型 | 建议周期 |
| --- | --- |
| 输出电流、电压、功率 | 1-2 秒 |
| 输入电压、输入功率、PF | 2-5 秒 |
| 温度、故障位 | 1-3 秒 |
| 型号信息 | 上电查询一次，后续按需 |
| 电能、亮灯时间 | 10-60 秒 |

双路时要控制总线负载。若一条命令从发送到响应平均 30 ms，一轮 10 条命令约 300 ms；实际还要预留响应超时和重试，因此不要把所有字段都设置成高频轮询。

### 4.6 UART2 错误处理

必须处理以下错误：

| 错误 | 处理 |
| --- | --- |
| 响应超时 | 当前命令重试，超过次数后通道离线 |
| checksum 错误 | 丢帧，本次命令按失败处理 |
| 帧头错误 | 丢弃直到找到下一个 `0x3A` |
| 帧尾错误 | 丢弃当前帧 |
| 长度超过上限 | 清接收状态 |
| 忙状态重复发送 | 返回 busy，业务层排队 |
| UART ORE/FE/NE 错误 | 清错误标志，重新启动接收 |
| 通道不匹配 | 丢弃或记录异常，不更新 snapshot |

通信离线判定：

```text
连续 N 次超时，或 last_rx_tick 超过 DP_CHANNEL_OFFLINE_MS
```

离线后：

- `snapshot[c].online = 0`
- 平台运行状态可标记异常。
- 告警层可生成“数字电源通讯异常/设备异常”类告警，如果中科协议没有专用告警码，则先映射到设备故障类。
- 周期性继续尝试查询型号或关键字段，恢复后自动上线。

### 4.7 代码风格和实现约束

数字电源新增代码应遵守以下规则，避免把临时验证代码带入正式工程：

- 模块名统一使用 `digital_power_` 或 `dp_` 前缀。
- 协议层只做帧构建和帧解析，不访问 MQTT、不访问中科 JSON。
- UART2 层只做字节收发、方向控制和错误恢复，不解析业务含义。
- Service 层负责队列、pending 请求、轮询、snapshot 更新。
- Alarm 层只读取 snapshot 并输出中科告警状态。
- 中断回调只做短逻辑：存字节、发下一个字节、置标志。
- 不在中断里打印日志。
- 不在中断里调用 JSON、MQTT、Flash 写入、复杂计算。
- 不使用动态内存。
- 所有缓冲区固定长度，并在写入前检查边界。
- 所有对外函数返回明确状态码，不用隐式全局变量表示成功失败。
- 单路和双路逻辑不得复制两份，应通过 `cns` 和 `channel_index` 参数复用。

## 7. 功能点对接

### 7.1 平台调光

平台下发：

```json
{
  "DT": {
    "cnCtrl": [
      {"cns": 1, "bri": 80, "last": 0}
    ]
  }
}
```

处理逻辑：

```text
cns=1
bri=80
level=80*2=160
cmd=0x3C
发送: 3A 3C 00 01 A0 DD 0D 0A
等待: 3A 3D 00 01 55 93 0D 0A
```

双路第二路：

```text
cns=2
cmd=0x3C | 0x80 = 0xBC
```

### 7.2 设置最大电流比例

如果平台或本地配置需要设置最大电流：

```text
cmd=0x31 或 0xB1
offset=0x00
len=0x01
data=0x00-0x64
```

应答：

```text
cmd=0x32 或 0xB2
data=0x55 表示成功
```

### 7.3 电参轮询

第一阶段建议轮询最小闭环字段：

| 字段 | 第一阶段建议命令 | 证据状态 | 用途 |
| --- | --- | --- | --- |
| 聚合数据 | `0x3A offset=0x00 data=0x1F` | 单路/双路模拟程序均有“读 0x3A 全部数据”，解析长度为 31 字节 | 优先作为最小闭环，减少 offset 猜测 |
| 输出电流 | 聚合帧 byte0-1；或 `0x3A offset=0x00 data=0x02` | 聚合帧已证实；单项查询在参考主机代码中存在 | 输出过流/欠流、上报 |
| 输出电压 | 聚合帧 byte2-3；或 `0x3A offset=0x01 data=0x02` | 聚合帧已证实；单项查询按钮存在 | 输出异常、上报 |
| 内部/外部 AD | 聚合帧 byte4/5；或 `0x3A offset=0x03/0x04 data=0x01` | 参考按钮存在；含义是 AD 值，不等同摄氏温度 | 温度换算待确认 |
| LED 输出功率 | 聚合帧 byte7-8 | 已在模拟程序聚合解析中出现 | 功率上报、亮灯判断 |
| 输入电流/电压/功率/PF | 聚合帧对应字段 | 已在模拟程序聚合解析中出现 | 电参上报、输入异常判断 |
| 内部/外部保护温度 | 聚合帧 byte25/26 | 已在模拟程序聚合解析中出现 | 过温告警 |
| 故障模式 | 聚合帧最后 1 字节 | 已在模拟程序聚合解析中出现，bit0 短路、bit1 开路、bit2 限功率 | 短路、开路、限功率 |

处理策略：

- 第一阶段优先使用 `0x3A offset=0x00 data=0x1F` 聚合查询，验证调光、查询、上报的最小闭环。
- 表中原先按 `0x0C/0x0D/0x0E/0x0F/0x12/0x13/0x15` 推导的单项 offset 不能直接作为正式协议结论，必须由厂家协议或实物抓包确认后再启用。
- 聚合帧字段单位必须逐项确认。模拟程序显示输出电压、输入电压单位为 `V`，当前中科 `EleInfo.v` 使用 `ac_voltage_8209` 的 `0.1V` 量纲，正式映射前要明确平台期望单位，不能只按变量名迁移。

### 7.4 型号信息

```text
cmd=0x35 或 0xB5
offset=0x0B
len=0x01
data=0x05
```

返回：

```text
cmd=0x36 或 0xB6
len=0x05
```

用于启动时确认数字电源在线、型号、额定功率、最大电流。

## 8. 告警迁移

### 8.1 可直接迁移的告警

| 中科告警 | 原工程来源 | 数字电源来源 | 迁移方式 |
| --- | --- | --- | --- |
| 输入过压 | `ac_voltage_8209` + `Error_3_OV` | 输入电压 `offset=0x0E` | 按配置阈值计算 |
| 输入欠压 | `ac_voltage_8209` + `Error_4_LV` | 输入电压 `offset=0x0E` | 按配置阈值计算 |
| 输出过流/过载 | `Io_value` / `Po_value` | 输出电流 `offset=0x00`、功率 `offset=0x06` | 按额定值或阈值计算 |
| 输出低压/异常 | `Vo_value`、`Io_value` | 输出电压 `offset=0x01`、输出电流 `offset=0x00` | 亮灯状态下判断 |
| 灯具开路/短路 | 本地计算 | 故障模式 `offset=0x15` bit0/bit1 | 直接映射 |
| 驱动过温 | `Ntctemp.Ntctemp` | 内部/外部 NTC `offset=0x12/0x13` | 按阈值计算 |
| 限功率/驱动异常 | 无稳定独立来源 | 故障模式 bit2 | 可作为设备故障或降额状态 |

### 8.2 不能直接迁移的告警

| 中科告警 | 原因 | 第一阶段策略 |
| --- | --- | --- |
| 漏电告警 | 数字电源协议未提供漏电采样 | 固定无告警或不上报 |
| 灯杆倾斜 | 当前项目也无对应传感器 | 不做 |
| 真实掉电告警 | CAT.1 断电后可能无法通信 | 用输入电压异常/数字电源离线近似 |

### 8.3 过温保护迁移策略

第一阶段：

```text
数字电源温度采样 -> CAT.1 判断阈值 -> 中科告警上报
```

不做：

```text
CAT.1 主动 PWM 降额
CAT.1 主动关断
```

原因：

- 数字电源本体通常已有硬件/固件保护。
- CAT.1 再主动降额可能与数字电源内部策略冲突。
- 项目目标是先打通平台与数字电源通讯闭环。

第二阶段可选：

```text
温度达到一级阈值 -> CAT.1 下发较低亮度
温度达到二级阈值 -> CAT.1 下发 0 亮度
恢复阈值以下 -> 恢复平台设定亮度
```

该策略必须经过电源厂家确认。

### 阶段 1：UART2 数字电源协议闭环

目标：

- UART2 能发送数字电源命令。
- 能解析单路和双路响应。
- 用模拟程序完成闭环验证。
- 明确半双工方向切换、响应超时、重试和通道匹配策略。

操作：

1. 实现 `digital_power_protocol`。
   - `digital_power_calc_checksum()`
   - `digital_power_build_frame()`
   - `digital_power_parse_frame()`
   - `digital_power_cmd_with_channel()`
   - `digital_power_channel_from_cmd()`
2. 实现 `digital_power_uart2`。
   - 初始化 USART2。
   - 配置数字电源波特率，默认按 `9600 8N1` 准备，最终以实物协议为准。
   - 默认接收方向。
   - 发送前清 RX 状态。
   - 发送时切 TX 方向。
   - 最后一字节发送完成后切回 RX 方向。

3. 实现半双工 pending 请求。
   - 保存 `cns/base_cmd/real_cmd/offset/expected_ack_cmd/start_tick/retry_count`。

   - 响应匹配后清 pending。
   - 超时后重试，超过次数标记失败。
4. 支持以下命令：
   - 调光 `0x3C`
   - 最大电流 `0x31`
   - 查询全部或查询输出电流/电压
   - 查询型号 `0x35`
5. 支持命令高位通道：
   - 一路：`cmd`
   - 二路：`cmd | 0x80`
6. 用模拟程序做最小闭环：
   - 单路模拟程序验证基础命令。
   - 双路模拟程序验证 `0x80` 高位和 `cmd & 0x7F` 解析。
   - 手动构造错误 checksum、错误帧尾、半帧超时。

验收：

- 单路模拟程序下，发送 `0x3C/0x31/0x3A/0x35` 有正确响应。
- 双路模拟程序下，`cns=2` 能看到 `cmd | 0x80`。
- 接收解析能正确识别 `channel` 和 `base_cmd`。

- 方向控制正确：发送时总线由 CAT.1 驱动，发送完成后能释放并收到数字电源响应。
- pending 请求正确：未收到响应前不会发下一条。

- `0x3C` 调光组帧正确。
- `0x31` 最大电流组帧正确。
- `0x3A` 查询组帧正确。
- `0x35` 型号查询组帧正确。
- `cmd | 0x80` 第二路组帧正确。
- `cmd & 0x7F` 接收解析正确。
- checksum 错误时丢帧。
- 帧头不是 `0x3A` 时丢帧。
- 帧尾不是 `0x0D 0x0A` 时丢帧。
- 长度不匹配时丢帧。

### 10.2 UART2 半双工验证

- 上电后 UART2 默认处于接收方向。
- 发送前方向脚切到 TX。
- 发送完成后方向脚切回 RX。
- 最后一个字节停止位发完后才释放总线。
- 切回 RX 后能立即收到模拟程序响应。
- 自发数据不会被当作响应解析。
- pending 未完成前，第二条命令不会抢占总线。
- 响应超时后按配置次数重试。
- 连续失败后通道进入离线状态。
- 恢复响应后通道能重新在线。
- 双路轮询时 CH1/CH2 不串路。

### 10.3 平台控制验证

- 平台下发开灯。
- 平台下发关灯。
- 平台下发亮度 1、50、100。
- 平台下发 `last=1` 恢复上次亮度。
- 双路分别下发 `cns=1`、`cns=2`。
- 双路同时下发两个 `cnCtrl`。

### 10.4 上报验证

- 输出电流上报正确。
- 输出电压上报正确。
- 输入电压上报正确。
- 输入功率上报正确。
- 功率因数上报正确。
- 电能上报正确。
- 亮灯时间上报正确。
- 单路数组和双路数组长度正确。

### 10.5 告警验证

- 输入过压触发/恢复。
- 输入欠压触发/恢复。
- 输出过流触发/恢复。
- 输出低压或开路触发/恢复。
- 短路故障位触发/恢复。
- 开路故障位触发/恢复。
- 过温触发/恢复。
- 数字电源离线触发/恢复。
- 漏电和倾斜第一阶段确认不上报或固定正常。

### 10.6 稳定性验证

- UART2 连续轮询 24 小时。
- 平台连续调光 1000 次。
- 数字电源断开再恢复。
- CAT.1 重启后重新查询型号和状态。
- MQTT 断线重连后状态重新上报。
- 双路情况下交替调光不串路。

## 11. 首先开始的阶段

建议第一步从“阶段 1：UART2 数字电源协议闭环”开始，而不是先改整套中科业务。

原因：

- 数字电源协议闭环是整个项目的基础。
- 单路/双路模拟程序已经具备验证条件。
- 先验证 UART2 组帧、解析、通道高位、超时恢复，可以降低后续平台对接风险。

阶段 1 完成后，再进入平台控制对接。这样每一步都有明确验收，不会同时改 UART2、MQTT、告警、计划任务导致问题难定位。

## 12. 待确认问题和风险处理

以下问题必须在阶段 1 或阶段 2 前关闭，不能留到整套平台联调时才发现。

| 问题 | 当前证据 | 风险 | 处理策略 |
| --- | --- | --- | --- |
| 数字电源正式协议是否等同模拟程序 | 参考工程和模拟程序可证明帧格式、checksum、部分命令；不能证明实物所有 offset 和单位 | 按模拟程序开发后，实物字段错位或单位错误 | 阶段 1 必须用串口抓包记录真实 `0x3C/0x31/0x3A/0x35` 收发帧 |
| 双路通道高位是否覆盖所有命令 | 双路模拟程序对部分命令加 `0x80`，但单项查询和型号查询存在不加高位的按钮 | CH2 查询可能实际读到 CH1 或无响应 | 建立命令级白名单，未验证的命令不用于 CH2 上报 |
| `0x3A` 单项 offset 表是否准确 | 聚合帧 31 字节解析明确；多个高 offset 是根据聚合字段位置推导，不是已验证单项读地址 | 单项轮询读错字段 | 第一阶段优先聚合查询；单项查询逐个抓包确认 |
| 温度字段是 AD 值还是摄氏度 | 参考代码同时出现“内部AD值/外部AD值”和“内部保护温度/外部保护温度” | 过温告警阈值错误 | 将 AD 值和摄氏温度分成不同 snapshot 字段，实物确认后再参与告警 |
| 平台电参单位 | 当前工程 `EleInfo` 读 BL0942/ADC 原始单位，数字电源模拟程序显示单位不同 | 平台显示错误或告警阈值错误 | 在迁移表中为每个字段写明“数字电源单位 -> 中科上报单位”的换算 |
| UART2 方向控制硬件 | 当前工程 UART2 被 BL0942 占用；是否有 485 DE/RE 或 USART 半双工硬件连接未在文档中完全证明 | 发送后无法收到响应，或自发回环被误解析 | 阶段 0 先确认原理图/IO，阶段 1 用逻辑分析仪或串口工具验证 TX/RX 切换 |
| 本地保护功能停用边界 | 文档计划停用 BL0942、PWM、ADC、NTC、漏电等主业务来源 | 如果硬件仍依赖本地保护，停用会降低安全性 | 区分“平台主数据源迁移”和“硬件保护是否保留”，安全保护需硬件负责人确认 |
| 中科双路上报形态 | 当前 `mqtt_zk_protocol.c` 多处仍按单路数组填充或 `cns=1` 处理 | 双路平台数据不完整或告警串路 | 阶段 2 前完成 `RunSts/EleInfo/LightTm/Alarm` 数组级改造清单 |

第一阶段最小闭环验收必须收集以下证据：

1. 单路：`0x3C` 调光、`0x31` 最大电流、`0x3A offset=0 len=1 data=31` 聚合查询、`0x35 offset=0x0B` 型号查询都有收发帧。
2. 双路：CH1/CH2 分别执行 `0x3C` 和 `0x3A offset=0`，确认 `cmd | 0x80` 和响应通道解析一致。
3. 错误路径：checksum 错误、帧尾错误、半帧超时、响应超时、pending 忙状态都有可观察日志或计数。
4. 单位映射：至少输出电流、输出电压、输入电压、输入功率、温度、故障位完成“原始字节 -> snapshot -> 中科上报值”的记录。

## 13. 最终交付标准

数字电源项目完成后，应满足：

- 同一套代码支持单路和双路数字电源。
- 4G 入网、MQTT、中科协议保持可用。
- UART2 只用于数字电源通讯。
- 本地 PWM 不再参与调光。
- BL0942 不再参与电参上报。
- 本地输出 ADC 不再参与电参上报。
- 数字电源采样成为平台运行状态和告警的主数据源。
- 中科 `cns=1/2` 与数字电源第 1/2 路严格对应。
- 所有平台控制、上报、告警均有模拟程序或实物验证记录。
