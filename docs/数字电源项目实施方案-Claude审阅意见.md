## 2. 主要问题清单

## 3. 协议核对结论

已能从参考工程确认：

- 帧格式为 `0x3A cmd offset len data... checksum 0x0D 0x0A`。
- checksum 为 `cmd + offset + len + data...` 的 8 位累加和，不包含帧头和帧尾。
- `0x3C` 调光请求对应 `0x3D` 应答，成功 data 为 `0x55`。
- `0x31` 最大电流比例请求对应 `0x32` 应答，成功 data 为 `0x55`。
- `0x3A` 查询请求对应 `0x3B` 应答。
- `0x35` 型号/比例查询请求对应 `0x36` 应答。
- 双路模拟程序接收解析时使用 `cmd & 0x7F`，说明固件解析层应该先拆 `channel/base_cmd`。

仍需确认：

- CH2 是否所有命令都按 `cmd | 0x80`。
- 单项 offset 是否与聚合帧字段位置一致。
- 聚合帧中的电压、电流、功率、温度、电能单位。
- 温度 AD 和保护温度是否是两类字段。

## 5. 建议的第一阶段最小闭环

第一阶段不要同时迁移 MQTT、告警、计划任务。建议只做 UART2 和协议闭环：

1. 实现 `digital_power_protocol`，只负责组帧、checksum、解析、通道高位拆分。
2. 实现 `digital_power_uart2`，只负责半双工收发、方向控制、接收状态机、错误恢复。
3. 实现最小 `digital_power_service`，只支持 pending、超时、重试、调光、最大电流、聚合查询、型号查询。
4. 用单路模拟程序验证 `0x3C/0x31/0x3A/0x35`。
5. 用双路模拟程序只验证已知加高位的命令：CH1/CH2 调光和 `0x3A offset=0` 聚合查询。
6. 抓取并保存至少 10 组正确帧、3 组错误帧、3 组超时重试日志。

验收标准：

- pending 未完成前不会发送下一条命令。
- 校验错、帧尾错、长度错、半帧超时都能丢帧并恢复。
- CH1/CH2 响应不会串路。
- 聚合帧 31 字节能完整解析到 snapshot。
- snapshot 到平台字段的单位映射有书面记录。

## 6. 后续实施建议

阶段 1 闭环通过后，再做以下迁移：

- 平台控制：`zk_apply_brightness()` 改为带 `cns`，再进入 `digital_power_set_brightness(cns, brightness)`。
- 计划任务：保留 `zk_work_plan.c` 的 `cns_mask`，按通道分别入队。
- 上报：`EleInfo/RunSts/LightTm` 按通道数组生成，不再读 BL0942/ADC 主数据。
- 告警：从 `g_dp_snapshot[cns - 1]` 计算输入过压/欠压、输出异常、短路、开路、限功率、过温；漏电和倾斜第一阶段固定正常或不上报。
- 稳定性：实物 24 小时轮询、断开恢复、连续调光、MQTT 重连后重报。
