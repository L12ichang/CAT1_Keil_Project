## 二、功能架构总览

```
MQTT收包
  ↓
zk_dispatch_message()
  → sv="plan" 匹配
    → zk_handle_plan_message()
      ├── CT="W" → zk_plan_upsert() → 解析/校验 → Flash双页写入
      └── CT="R" → zk_plan_handle_read()
            ├── DO="nid" → 返回有效计划ID列表
            ├── DO="now" → 返回当前匹配计划(简略版)
            ├── DO="del" + id → 删除单条计划
            └── id=N → 返回单条计划完整内容

主循环每轮:
  zk_work_plan_process()
    → zk_plan_find_current_match()
      遍历 plans[0..7]:
        有效? 已启用? type==1? → 日期范围内? → 星期匹配? → 精确分钟匹配?
      最高优先级获胜
    → zk_apply_plan_brightness()
    → 记录已执行防重入
```

## 三、与协议的差异（仅type=1相关）

### 差异 #1 — 删除命令格式不匹配  【严重】

| 项目   | 协议规定                  | 代码实现                             |
| ------ | ------------------------- | ------------------------------------ |
| CT     | `"W"` (7.13.2)          | `"R"` (代码只在R路径处理)          |
| DT格式 | `"del": [1,3,5]` (数组) | `"DO": "del"` + `"id": 1` (单条) |

**协议原文** (7.13.2):

```json
{"CT":"W", "DT":{"del":[1,3,5]}}
```

**代码实际处理** (`zk_work_plan.c:1162-1178`):

```c
// 仅在 CT=R 路径下
if (strcmp(do_node->valuestring, "del") == 0) {
    id_node = cJSON_GetObjectItem(dt, "id");  // 单条id
    ...
}
```

**后果**: 服务器按协议标准下发删除指令，会被当作计划下发(write)→解析失败→回错误码。删除功能实际不可用。

---

### 差异 #2 — "当前运行计划"查询不匹配  【中等】

**查询格式**:

| 项目 | 协议规定 (7.9.2) | 代码实现        |
| ---- | ---------------- | --------------- |
| 请求 | `"now": cns`   | `"DO": "now"` |

**响应格式**:

| 项目 | 协议规定 (7.9.3)                                           | 代码实现                                                |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------- |
| 响应 | 完整plan对象 (含en/id/type/priority/sDate/eDate/week/jobs) | `{id, jobIndex, actionIndex, bri, priority}` 简略字段 |

代码 (`zk_plan_build_now_dt` line 1080-1102)：

```c
cJSON_AddNumberToObject(now, "id", match->id);
cJSON_AddNumberToObject(now, "jobIndex", match->job_index);
cJSON_AddNumberToObject(now, "actionIndex", match->action_index);
cJSON_AddNumberToObject(now, "bri", match->bri);
cJSON_AddNumberToObject(now, "priority", match->priority);
```

**后果**: 服务器查询当前运行计划会收到错误响应。

---

### 差异 #3 — 回复中缺失类型无关字段  【轻微】

协议7.7.3的查询回应JSON中包含 `setoffset` / `riseoffset` / `dayen` / `onLux` / `onWindow` / `offLux` / `offWindow` 字段。代码的 `zk_plan_record_to_json` 不生成这些字段（它们对type=1无意义）。如果服务器端做严格的schema校验会失败。

## 四、已确认的Bug

### Bug #1 — en=0 禁用计划时销毁全部数据  【严重】

**位置**: `zk_work_plan.c:589-614`, `zk_work_plan.c:724-748`

**根因**: `zk_plan_parse_enabled` 在 `en==0` 时直接 return 0，但此前已 `memset(out, 0, sizeof(*out))`。随后 `zk_plan_upsert` 用这个半空的结构体覆盖了 Flash 中的整条记录。

```c
// zk_plan_parse_enabled
memset(out, 0, sizeof(*out));    // 全部清零
out->valid = 1;
out->id = ...;
out->en = 0;
if (out->en == 0) return 0;      // 提前返回，其它字段全是0

// zk_plan_upsert
next = zk_plan_store;
next.plans[record.id - 1] = record;  // ❌ 覆盖了原有的完整配置
```

**影响**: 禁用一条计划后，其所有配置（日期、星期、时间点、亮度值）全部丢失。重新启用时即使 `en=1` 也无法恢复，必须重新下发全部字段。

**协议依据** (7.4.5): "当en=0时，其他字段可省略" — 协议设计意图是"只关不停"，保留配置。

---

### Bug #2 — 删除命令无法通过标准协议路径触发  【严重】

即 协议差异#1。CT=W + DT.del 在代码中无处理路径。

**影响**: 平台无法正常删除设备端的工作计划。

---

### Bug #3 — "now"查询命令格式与协议不符  【中等】

即 协议差异#2。平台发 DT.now=cns 过来，代码不识别。

**影响**: 平台无法查询当前生效的工作计划。

---

### Bug #4 — 年循环 (0xFFFF) 模式下闰年判断不正确  【轻微】

**位置**: `zk_work_plan.c:267-269`

```c
static int zk_plan_is_leap_year(u16 year)
{
    if (year == 0xffff)
        year = 2024;         // 硬编码2024（闰年）
    ...
}
```

**影响**: 如果设置 `sDate="FFFF-02-29"` 且 `eDate="FFFF-02-29"`（每年2月29日执行），则在非闰年（2025、2026、2027...）时 `zk_plan_days_in_month` 会返回 29 通过验证。但实际 `GetWeek` 传入 2月29日 不会报错，匹配时会出现日期溢出——C标准库 `getWeek` 用蔡勒公式接受 year/mon/day 参数，非闰年2月29日计算出的星期是错误的。

不过实际场景中几乎不会有人配2月29日的工作计划。属于理论bug。

---

### Bug #5 — 分钟级精确匹配无容错窗口  【轻微】

**位置**: `zk_work_plan.c:903`

```c
if (action->minute != minute) continue;
```

**根因**: 裸机超级循环中，如果一轮循环因4G AT指令、Flash操作等延迟超过1秒，RTC分钟可能已跳变，导致计划错过触发窗口。

**影响**: 小概率漏执行一次调光动作。因为是周期性计划，下一分钟/下一天会重新匹配，不会永久丢失。

## 五、不合理的设计

### 1. cns_mask (通道选择) 被解析存储但从不使用

`zk_plan_job_t.cns_mask` 在 JSON 解析 (`zk_plan_parse_cns`) 和序列化回 JSON (`zk_plan_record_to_json`) 中完整处理，但在匹配执行路径 `zk_plan_find_current_match` → `zk_apply_plan_brightness` 中完全被忽略。

当前 `ZK_CNCTRL_SUPPORTED_CNS=1`（单通道设备），所以功能上没有错误。但：

- 浪费 1 字节/每条记录
- 浪费 8 字节/每个计划
- 代码读者会困惑：为什么解析了却不使用？
- 如果未来硬件升级到多通道，这个地方会有隐蔽的bug

**建议**: 当前保持单通道逻辑不变，但在将来多通道实现时务必修正此处。

---

### 2. 每次 `en=0` 做完整 Flash 双页擦写

**位置**: `zk_work_plan.c:165-186`

仅为了改一个 `en` 字段，就要擦写两个 1KB Flash 页（主+备）。STM32F103 Flash 寿命约 10K 次。

如果平台频繁切换计划启停（如调试阶段），会加速 Flash 磨损。

**建议**: 短期内无需优化（10K 次对低频场景够用），但如果计划数增多或频繁切换启用状态，考虑在RAM中做dirty标记后批量写入。一般不会进行计划的变更，除非测试阶段。

---

### 3. 响应中缺少执行日志

当 `zk_work_plan_process` 匹配到计划并调整亮度时，没有任何 `printf` 或日志输出。

对于一个无人值守的IoT路灯控制器，远程排查"计划为什么没执行"或"什么时候执行的"非常困难。无法区分以下情况：

- RTC未同步导致不匹配
- 日期/星期条件不满足
- 确实触发了但亮度不对

**建议**: 执行时打印关键信息，通过串口/日志主题透出。

---

### 4. `zk_plan_find_current_match` 优先级逻辑反转隐患

```c
if (match->found == 0 || plan->priority > match->priority)
```

数值越大优先级越高。但协议 (7.2) 定义 priority 范围为 1~8，没有定义方向。如果服务器端认为 "1 是最高优先级" 而代码认为 "8 是最高优先级"，会产生预期之外的计划抢占。

**建议**: 在接口文档或代码注释中明确方向。当前是代码在上、协议未定义，有歧义风险。

---

### 5. 结构体缺少 packed 属性

`zk_plan_record_t`/`zk_plan_job_t`/`zk_plan_action_t` 混用 `u8`/`u16`，没有 `__attribute__((packed))`。

STM32F103 是 Cortex-M3，默认对齐是 4 字节，所以 `u8` 后面跟 `u16` 可能会插入1字节padding。不同编译器版本/优化等级的行为可能不同。Flash中存储的二进制布局一旦因编译器变化而改变，固件升级后新老版本无法互相读取工作计划数据。

**建议**: 加 `__attribute__((packed))` 确保布局确定。

## 七、总结

**当前周日期工作计划 (type=1) 的核心链路是正确的**：

- JSON 解析校验完整（与协议错误码对应）
- 双页 Flash 备份 + 魔数/版本/校验保护，存储可靠
- 日期范围 + 星期掩码 + 分钟匹配逻辑正确
- 年循环 (0xFFFF) 跨年区间判断正确
- 防重入执行机制有效

**需要优先修复三个问题**：

1. `en=0` 不要销毁数据（当前最严重的bug）
2. 删除命令匹配协议格式（当前功能不可用）
3. `now` 查询与协议对齐（当前协议字段不匹配）

**整体评价**: 代码质量中等偏上，存储可靠性设计是亮点。主要问题是与协议文档存在几处具体差异，以及禁用计划的隐蔽数据丢失bug。把这几个点修完，周日期工作计划功能就完整可用了。
