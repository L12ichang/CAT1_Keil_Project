## 2. 问题一：packed 结构体成员地址不能传给普通 u16 指针

### 编译错误

Keil 在 `Core/Src/LampProtocolLib/zk_work_plan.c` 中报错：

```text
zk_work_plan.c(333): error: #167:
argument of type "__packed u16 *" is incompatible with parameter of type "u16 *"

zk_work_plan.c(590): error: #167:
argument of type "__packed u16 *" is incompatible with parameter of type "u16 *"

zk_work_plan.c(600): error: #167:
argument of type "__packed u16 *" is incompatible with parameter of type "u16 *"
```

### 根因

`zk_work_plan.c` 中的工作计划存储结构使用了 packed 布局：

```c
typedef struct __attribute__((packed))
{
    u16 year;
    u8 mon;
    u8 day;
    u8 hour;
    u8 min;
    u8 sec;
    u8 reserved;
} zk_plan_datetime_t;

typedef struct __attribute__((packed))
{
    u16 minute;
    u8 bri;
    u8 reserved;
} zk_plan_action_t;
```

packed 结构体用于保持 Flash 存储布局紧凑和稳定，但 packed 成员不保证天然对齐。Keil ARMCC 对这类成员取地址非常严格，例如：

```c
zk_plan_parse_year(text, &dt->year);
zk_plan_parse_duration(schedule_item, &out->actions[index].minute);
zk_plan_parse_time_text(schedule_item->valuestring, &out->actions[index].minute);
```

这里 `&dt->year` 和 `&out->actions[index].minute` 的实际类型会被 Keil 视为：

```text
__packed u16 *
```

但解析函数参数要求的是普通：

```text
u16 *
```

因此 Keil 拒绝编译。

### 修复方式

改为使用局部 `u16` 变量接收解析结果，再赋回 packed 字段：

```c
u16 year;

if (zk_plan_parse_year(text, &year) != 0 ||
    ...)
{
    return 8;
}
dt->year = year;
```

工作计划动作分钟数同理：

```c
u16 minute;

err = zk_plan_parse_duration(schedule_item, &minute);
...
out->actions[index].minute = minute;
```

### 影响评估

该修复不改变：

```text
1. 工作计划 JSON 字段
2. 工作计划解析错误码
3. 工作计划存储结构字段
4. packed 结构体布局
5. Flash 数据兼容性
6. 最终 year/minute 的计算结果
```

本质只是避免直接把 packed 成员地址传给普通指针参数，属于 Keil 编译兼容性修复。

## 3. 问题二：zk_plan_delete 缺少前置声明

### 编译告警

Keil 报出：

```text
zk_work_plan.c(887): warning: #223-D:
function "zk_plan_delete" declared implicitly
```

### 根因

`zk_plan_delete()` 的定义位于文件后部，但在前面处理 `del` 数组时已经调用：

```c
del_err = zk_plan_delete(item->valueint);
```

在调用点之前没有函数原型声明。Keil 按旧 C 规则给出隐式声明告警，这类问题容易掩盖真实参数或返回值不匹配风险。

### 修复方式

在文件静态变量区域前后增加前置声明：

```c
static int zk_plan_delete(int id);
```

### 影响评估

该修复不改变函数实现、不改变调用逻辑、不改变协议行为，只消除隐式声明风险。

## 5. 非代码问题：原路径下 Keil 命令行 via 文件错误

本次最开始在原工程路径：

```text
D:\keil work\CAT1_Keil_Project\CAT1_Keil_Project
```

直接调用 Keil 命令行时出现大量错误：

```text
Fatal error: C3904U: Could not open via file 'out\xxx.__i'.
```

该问题不是业务代码错误，判断依据：

```text
1. out 目录本身可写，手动创建 .__i 文件成功
2. 复制到无空格临时路径后，该错误消失
3. 无空格路径下 Keil 能进入正常源码编译阶段
```

因此该问题更像是 Keil/uVision 命令行在带空格路径、并行构建或已有 UV4 进程状态下，对 ARMCC via 文件处理不稳定。

建议后续自动化 Keil 构建时使用无空格路径，例如：

```text
D:\codex_keil_build_xxx\CAT1_Keil_Project
```

或者在 Keil GUI 中手动 Rebuild，避免命令行路径问题干扰真实编译结果。

## 6. 最终结论

本次 Keil 编译暴露的真实代码问题只有两类：

```text
1. packed 结构体 u16 成员取地址传参不兼容 Keil ARMCC
2. zk_plan_delete 缺少前置声明导致隐式声明告警
```

已修复且不改变功能、不改变协议、不改变 Flash 布局、不改变计算结果。
