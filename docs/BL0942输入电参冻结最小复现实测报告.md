# BL0942 输入电参冻结故障最小复现实测报告

> 测试日期：2026-08-10
> 测试基线：`229a722119ff40d62394653667503badcc5e21cc`
> 测试设备：STM32F103/HK32F103 板卡 + BL0942 + J-Link 601012592
> 测试目的：验证“一次真实 USART2 ORE 经当前 ErrorCallback + dummy RX 恢复逻辑演化为永久冻结”的假设

## 1. 最终裁决

**裁决：部分成立，但不足以解释现场永久冻结；“单次 ORE 自循环就是现场根因”的假设未被确认。**

5 次注入均真实产生了 USART2 ORE，并造成有效帧暂时停止：

- 第 1、3、4、5 次在 3 秒快照仍无新有效帧，但 10 秒快照已自行恢复；
- 第 2 次在 30 秒快照仍无新有效帧，ORE 累计到 301；
- 第 2 次在人工恢复命令执行前已经自行恢复，恢复时间位于注入后约 30～46 秒之间；
- 5 次最终都无需 USART2 软件恢复、MCU Reset 或整机掉电即可重新取得有效帧。

因此实测证明：

```text
一次漏挂 RX
→ 真实 ORE
→ ErrorCallback / dummy RX 连锁
→ 数秒至数十秒的输入电参冻结
→ 当前代码最终仍可能自行恢复
```

但没有得到实施文档要求的关键证据：

```text
frame_ok 永久停止
且只有 force UART recover 才恢复
```

所以不能把此次单次 ORE 机制直接写成现场“运行 1～3 天后永久固定、直到断电才恢复”的根因。

## 2. 与上一轮调查结论的核对

| 上一轮结论                                                       | 本次复现后的裁决                                                       |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 故障域位于 BL0942/USART2，有效输入帧停止后 MQTT 会继续使用最后值 | **仍成立**                                                       |
| MQTT 数据新鲜度缺失是根因                                        | **仍否定；它只放大表现**                                         |
| USART2 缺少完整失败闭环是风险                                    | **成立；本次出现 12～284 次 ORE 连锁和最长超过 30 秒的采样中断** |
| 一次标准 ORE 足以形成永久冻结                                    | **本次 5/5 未复现，不能确认**                                    |
| 最近 4G Reset 是百台设备共同触发                                 | **仍无证据支持**                                                 |
| 现场第一次异常由什么触发                                         | **仍未确认**                                                     |

更准确的合并结论是：

> USART2 恢复设计确有缺陷，能够把一次异常放大为 ORE 风暴和短时电参冻结；但本次没有证明它会稳定永久化。现场长期不恢复还需要额外条件，或存在 BL0942 芯片/供电域等另一种冻结形态。

## 8. 注入方法

每次仅执行：

```text
g_bl0942_repro_inject_once = 1
```

下一帧接收到第 4 个字节后，`HAL_UART_RxCpltCallback()` 直接返回一次，不重新调用 `HAL_UART_Receive_IT()`。BL0942 继续发送剩余字节，使 USART2 硬件产生真实 ORE。

没有直接调用 `HAL_UART_ErrorCallback()`，没有 ISR printf、HAL_Delay、断点单步或长时间暂停 CPU。

## 10. 电参和 MQTT 观察

每次 `frame_ok` 停止期间，`ac_voltage_8209/ac_current/Z_ac_current/ac_powerpa` 保持上一有效值；有效帧恢复后重新变化，成功复现了“新报文读取最后输入值”的短时形态。

`nb_mqtt_pub_success_count` 在整组测试中从 3 增加到 8，`nb_mqtt_recovery_start_count` 始终为 0，Tick 和主循环持续推进。说明注入没有让 MCU、4G 或 MQTT 状态机整体停止。

限制：最长一次 30 秒冻结窗口内没有新的 PUBACK 计数，且没有本次 Broker 原始导出，因此不能声称已经独立证明“冻结窗口内平台收到新报文”；这里只能确认 MQTT 在注入前后持续工作，且代码仍读取最后有效输入全局量。

## 11. USART2、MCU Reset 和整机掉电恢复

### 注入产生的冻结

- 5 次最终都自行恢复；
- 第 2 次人工恢复命令执行前已经恢复，不能把恢复归因于 `force_recover`；
- 因此没有在“仍冻结”的注入现场完成 MCU Reset 或整机掉电对比。

### 本轮开始时另一次无 RX 状态

在用户重新整机上电前，原始和诊断固件均表现为：

```text
read_start/timeout 持续增加
RX complete = 0
frame_ok = 0
USART2 软件恢复无效
MCU/外设 Reset 无效
整机重新上电后立即恢复
```

这个形态更偏向 BL0942 芯片/供电域未工作，而不是单纯 MCU HAL 状态。但当时没有同步测量 BL0942 VDD，无法排除测试前整机输入电源未完全接通，因此它只能作为后续鉴别线索，不能直接认定为现场自然冻结。

## 12. 根因假设判定

| 假设                                          | 判定                             |
| --------------------------------------------- | -------------------------------- |
| 一次漏挂 RX 能产生真实 ORE                    | **确认，5/5**              |
| 当前 ErrorCallback + dummy RX 会形成 ORE 连锁 | **确认，5/5**              |
| ORE 连锁会让输入有效帧暂时停止                | **确认，5/5**              |
| 一次 ORE 会稳定永久冻结直到软件恢复/掉电      | **本次否定，0/5**          |
| 该机制就是现场 1～3 天永久冻结根因            | **证据不足，不能确认**     |
| USART2 恢复设计需要修复                       | **确认；最长异常超过30秒** |

## 13. 下一步建议

### 可以立即进行的健壮性修复

1. 检查全部 `HAL_UART_Transmit_IT/Receive_IT` 返回值。
2. 连续 2～3 个采样周期无有效帧时，在主循环完整执行 USART2 Abort、RCC 复位、重新初始化和状态清理。
3. 增加 `last_valid_frame_tick`，不要使用成功一次后永久为真的 `bl0942data_ready` 判断活性。
4. 修正看门狗异常计数被每个正常主循环清零的问题。
5. MQTT 上报增加数据年龄/有效性字段，避免把冻结值伪装成实时数据。

这些改动能消除本次已证实的 3～46 秒异常，但不能替代现场根因取证。

### 现场根因继续取证

下一台自然冻结设备应在断电前同时记录：

- BL0942 VDD、USART2 RX/TX 波形；
- USART2 `SR/DR/CR1/CR3` 和 HAL `gState/RxState/ErrorCode`；
- `read_start/frame_ok/last_ok_tick/ORE/FE/NE/timeout`；
- 先执行完整 USART2 重建，再 MCU Reset，最后才整机掉电；
- 区分“BL0942仍回包但MCU无法形成有效帧”和“BL0942完全不回包”。

只有前一种支持继续锁定 MCU USART2/HAL；后一种应重点检查 BL0942 状态、供电域、电源瞬态和芯片复位方式。
