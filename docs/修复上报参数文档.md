# 修复上报参数文档

> 项目：CAT.1 智慧电源（中科协议版）  
> 工程：`MDK-ARM-8008000`  
> 目标：修复登录上报、变化上报、周期上报中的参数口径问题，保持实现简单、非阻塞，符合低频交互 LED 驱动电源的运行特点。

---

## 1. 修复范围

本次修复只聚焦中科协议上报参数，不扩大到整体协议重构。

| 上报类型 | 协议 | 代码入口 | 本次关注点 |
|---|---|---|---|
| 登录上报 | `SV="rept", CT="L"` | `zk_make_login_packet()` | 设备信息字段、调光配置字段 |
| 周期上报 | `SV="rept", CT="C"` | `zk_publish_runtime_report(ZK_CT_CYCLIC)` | 运行时间、亮灯时间、运行状态、电气参数 |
| 变化上报 | `SV="rept", CT="B"` | `zk_publish_runtime_report(ZK_CT_CHANGE)` | 与周期上报共用数据源，状态变化后延迟稳定上报 |

不建议在本阶段改动 MQTT 会话状态机、JSON 路由框架、OTA、工作计划执行引擎。

---

## 2. 修复原则

### 2.1 不阻塞

LED 驱动电源属于低频状态交互设备，上报不是实时控制闭环，不应为了等待采样稳定而阻塞主循环。

要求：

- 不使用 `delayMs()` 等阻塞等待来凑最终数据。
- 不在上报函数里循环等待 ADC、BL0942、PWM 渐变完成。
- 变化上报继续使用现有 3 秒非阻塞稳定窗口。
- 上报失败时保留 pending 状态，下一轮主循环重试，不在当前调用里死等。

现有变化上报稳定窗口参照：

- `ZK_CHANGE_REPORT_SETTLE_MS = 3000UL`
- `zk_notify_state_changed()` 只标记变化和刷新时间点。
- `zk_mqtt_session_process()` 到时间后再发送 `CT="B"`。

### 2.2 低频统计

运行时间、亮灯时间建议按分钟级统计，不需要毫秒级精度。

要求：

- RAM 中可以按秒或分钟累计。
- Flash 只做低频保存，例如 6 小时、12 小时、掉电前或已有系统数据保存点。
- 不要每秒写 Flash。
- 不要扩展 `sys_data_st` 结构体，避免破坏当前 408 字节大小约束；需要持久化时使用独立小记录或复用已有低频保存机制。

### 2.3 数据源单一

上报层不要自己重新计算硬件状态，只从已经稳定的运行变量读取。

建议新增一个轻量运行统计模块，或者在 `mqtt_zk_protocol.c` 内部增加少量静态状态：

- 当前上电运行分钟数。
- 当前上电亮灯分钟数。
- 历史总运行分钟数。
- 历史总亮灯分钟数。
- 上一次统计 tick。
- 上一次亮灯状态。

不要新增任务线程，不要新增复杂调度器。

### 2.4 真实数据原则

上报参数必须来自真实采集源、真实运行状态或明确的协议配置，不能为了凑字段而填固定值。

基本规则：

- 有硬件采集源、驱动变量和单位换算依据的字段，可以上报。
- 只有配置含义的字段，例如额定功率、调光方式、经纬度配置，可以按当前配置上报。
- 没有硬件、没有驱动、没有 AT 查询结果的字段，不应上报。
- `0` 不能作为“不支持”的占位值；只有真实测量值就是 0，才允许上报 0。
- 如果协议要求字段但当前硬件不支持，应和平台确认“不上报该字段”或“平台忽略该字段”，不要设备端伪造正常值。

字段真实性判断标准：

| 字段类型 | 可以上报的条件 | 不允许的做法 |
|---|---|---|
| 电压、电流、功率 | 来自 BL0942 或 ADC，单位换算清楚 | 没有确认 AC/DC 口径就混用 |
| 运行时间、亮灯时间 | 来自本机 tick 和亮灭状态累计 | 当前亮就直接等于运行时间，当前灭就填 0 |
| 运行状态、亮度 | 来自实际 PWM/调光状态源 | PWM 已满功率但 `dim_level` 仍为 0 |
| 温度 | 来自 NTC 采样 | 没有传感器时填固定温度 |
| 光照 | 有光照传感器或真实输入 | 没有光照硬件时填 0 |
| 姿态角度 | 有倾角/加速度传感器 | 没有姿态硬件时填 `x/y/z=0` |
| 信号信息 | 来自模组 AT 查询 | 用固定 `cellid/pci/snr=0` 冒充真实网络信息 |

真实数据获取方式要写进代码注释或开发记录，至少说明：

- 原始变量来自哪个驱动文件。
- 原始单位是什么。
- 上报前做了什么换算。
- 平台最终显示单位是什么。
- 不支持的字段为什么不上报。

## 3. 当前问题点与参照点

### 3.1 登录上报字段不完全符合协议

问题：

- 协议文档字段为 `prodtp`，当前代码使用 `prottp`。
- 协议登录上报的调光配置包含 `dimTp`，当前登录 `Dim` 中没有带 `dimTp`。

代码参照：

- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`
- `zk_make_login_packet()`
- 当前格式片段：

```c
"DevInfo":{"protId":%d,"clas":"%s","prottp":"%s","hver":%d,"sver":%d}
"Dim":[{"cns":%d,"polar":%d,"dlmt":%d,"ulmt":%d,"rti":%d,"rtPwr":%d}]
```

修复建议：

- 将登录上报中的 `prottp` 改为 `prodtp`。
- `Dim` 增加 `dimTp` 字段，和属性读取 `zk_add_dim_prop()` 保持一致。
- 不改变 `zk_device_config_t` 数据结构，只改 JSON 字段名和输出字段。

修复后期望：

```json
"DevInfo":{"protId":100,"clas":"MS-SLC-01","prodtp":"iX7-075SC028-4G","hver":100,"sver":100}
"Dim":[{"cns":1,"dimTp":0,"polar":0,"dlmt":1000,"ulmt":9000,"rti":0,"rtPwr":200}]
```

优先级：高。  
复杂度：低。  
阻塞风险：无。

### 3.2 上电满功率运行与上报状态不一致

问题：

设备上电后当前会直接按 100% 输出：

```c
if(softstar)
{
    softstar=0;
    sys_pwm_fade_output(0, 100);
}
```

但上报运行状态读取的是 `dim_level`：

```c
return (dim_level > 0U) ? 31 : 32;
```

如果上电满功率输出没有同步 `dim_level`，平台会看到：

- 实际：灯已亮，100% 输出。
- 上报：`RunSts.sts[0] = 32`，`RunSts.bri[0] = 0`。

代码参照：

- `Core/Src/main.c`
- `Core/Src/gateway/net_dim.c`
- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`

修复建议：

低风险做法：

1. 上电软启动时不要直接只调用 `sys_pwm_fade_output(0, 100)`。
2. 同步设置运行状态源，例如将 `dim_level` 初始化为 100。
3. 尽量复用现有调光入口，避免 PWM 输出和协议状态分成两套。

建议实现形态：

```c
dim_level = 100;
sys_pwm_fade_output(0, 100);
```

或封装一个很小的启动函数：

```c
static void app_startup_full_power(void)
{
    dim_level = 100;
    sys_pwm_fade_output(0, 100);
}
```

注意：

- 不建议调用 `zk_apply_brightness(100)` 作为上电默认动作，因为它会触发 `zk_notify_state_changed()`，可能导致刚上线就产生变化上报。
- 上电默认满功率属于启动状态初始化，不应被当成远程调光事件。

优先级：高。  
复杂度：低。  
阻塞风险：无。

### 3.3 运行时间 `RunTm` 语义错误

协议语义：

| 字段 | 协议含义 | 单位 |
|---|---|---|
| `RunTm.tTime` | 设备总运行时间 | 分钟 |
| `RunTm.rTime` | 设备本次上电运行时间 | 分钟 |

当前代码：

```c
total_minutes = Timer_GetTickCount() / 60000UL;
cJSON_AddNumberToObject(run_tm, "tTime", (double)total_minutes);
cJSON_AddNumberToObject(run_tm, "rTime", (double)total_minutes);
```

问题：

- `tTime` 和 `rTime` 完全相同。
- 两者都只是本次上电 tick，不是设备历史总运行时间。
- 掉电重启后 `tTime` 也会从 0 重新开始。

代码参照：

- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`
- `zk_add_runtime_time_groups()`

修复建议：

维护两个变量：

```c
static uint32 zk_boot_run_minutes;
static uint32 zk_total_run_base_minutes;
```

计算方式：

```c
zk_boot_run_minutes = Timer_GetTickCount() / 60000UL;
RunTm.rTime = zk_boot_run_minutes;
RunTm.tTime = zk_total_run_base_minutes + zk_boot_run_minutes;
```

持久化策略：

- 阶段 1 可以先修 `rTime` 和字段语义，`tTime` 暂时等于本次上电，并在文档中标注未持久化。
- 阶段 2 再将 `zk_total_run_base_minutes` 做低频持久化。
- 不要把新字段直接塞进 `sys_data_st`，避免破坏结构大小。
- 如果需要持久化，使用独立小 Flash 记录，主备双副本即可。

优先级：高。  
复杂度：中。  
阻塞风险：无，前提是不高频写 Flash。

### 3.4 亮灯时间 `LightTm` 计算错误

协议语义：

| 字段 | 协议含义 | 单位 |
|---|---|---|
| `LightTm.tLtTime[]` | 历史亮灯总时间 | 分钟 |
| `LightTm.rLtTime[]` | 当次亮灯总时间 | 分钟 |

当前代码：

```c
light_minutes = (dim_level > 0U) ? total_minutes : 0UL;
```

问题：

- 如果开机亮了 10 分钟后关灯，上报亮灯时间会变成 0。
- 如果关灯 10 分钟后开灯，上报亮灯时间会直接变成 10。
- 它没有统计“亮灯区间”，只是把当前运行时间按当前开关状态复制了一次。
- `tLtTime` 和 `rLtTime` 也没有区分历史累计和本次上电累计。

代码参照：

- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`
- `zk_add_runtime_time_groups()`
- `RunSts` 使用 `dim_level` 判断亮灭。

修复建议：

增加一个非阻塞统计函数，在主循环或 `zk_mqtt_session_process()` 前段低频执行：

```c
static uint32 zk_light_last_tick;
static uint32 zk_boot_light_seconds;
static uint32 zk_total_light_base_minutes;

static void zk_runtime_counter_process(void)
{
    uint32 now = Timer_GetTickCount();
    uint32 elapsed_ms;

    if (zk_light_last_tick == 0) {
        zk_light_last_tick = now;
        return;
    }

    elapsed_ms = now - zk_light_last_tick;
    if (elapsed_ms < 1000UL) {
        return;
    }

    zk_light_last_tick = now;
    if (dim_level > 0U) {
        zk_boot_light_seconds += elapsed_ms / 1000UL;
    }
}
```

上报时：

```c
rLtTime[0] = zk_boot_light_seconds / 60UL;
tLtTime[0] = zk_total_light_base_minutes + rLtTime[0];
```

注意：

- 统计函数只做整数加法，不做 JSON，不发 MQTT，不写 Flash。
- 上报函数只读当前统计值，不临时计算亮灯时间。
- 多回路暂不扩展复杂数组，当前硬件只有一路时只填 `[0]` 下标；如果协议后续要求多路，再统一扩展。

优先级：高。  
复杂度：中。  
阻塞风险：无。

### 3.5 电流、电压口径需要确认：交流输入侧还是直流输出侧

当前上报：

```c
cJSON_AddItemToArray(c, cJSON_CreateNumber((double)Z_ac_current));
cJSON_AddItemToArray(v, cJSON_CreateNumber((double)ac_voltage_8209));
```

数据源：

| 字段 | 当前变量 | 来源 | 单位 |
|---|---|---|---|
| `EleInfo.c[0]` | `Z_ac_current` | BL0942 交流输入电流，带容性校正 | mA |
| `EleInfo.v[0]` | `ac_voltage_8209` | BL0942 交流输入电压 | 0.1V |
| 未上报 | `Io_value` | MCU ADC 直流输出电流 | mA |
| 未上报 | `Vo_value` | MCU ADC 直流输出电压 | 0.1V |

代码参照：

- `Core/Src/sys_bl0942.c`
- `Core/Src/sys_Vo_Io.c`
- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`

判断：

- 如果中科平台 `EleInfo` 定义的是“市电/输入侧电能信息”，当前 `Z_ac_current/ac_voltage_8209` 方向基本合理。
- 如果平台要看“灯具输出电流/输出电压”，当前上报就是口径错误。
- 由于协议字段只写“电流/电压”，没有明确 AC/DC，必须和平台确认口径。

低复杂度修复方案：

方案 A：保持协议 `EleInfo` 为输入侧。

- `EleInfo.c/v/p/f/rEc/tEc` 继续使用 BL0942。
- 文档明确这是输入侧电参。
- 输出侧 `Vo_value/Io_value/Po_value` 只用于保护和告警，不进中科标准上报。

方案 B：平台要求输出侧。

- 将 `EleInfo.c/v/p` 改为 `Io_value/Vo_value/Po_value`。
- `f/rEc/tEc` 不再能和输出侧完全对应，需要保留输入侧或置固定值会造成语义混乱。
- 不建议这样混用，除非平台明确 `EleInfo` 就代表输出侧。

方案 C：兼容扩展。

- 标准 `EleInfo` 继续输入侧。
- 如平台允许私有字段，再增加 `DcInfo` 或扩展字段上报输出侧。
- 这需要平台确认，不建议设备端单方面增加字段。

推荐：

先采用方案 A，并把协议口径写清楚。若客户平台明确要求输出侧，再走方案 C，避免破坏标准 `EleInfo`。

真实数据获取说明：

| 数据 | 真实来源 | 代码位置 | 上报前要求 |
|---|---|---|---|
| 输入电压 | BL0942 `V_RMS` | `sys_bl0942.c` -> `ac_voltage_8209` | 确认单位为 0.1V |
| 输入电流 | BL0942 `I_RMS` + 容性校正 | `sys_bl0942.c` -> `Z_ac_current` | 确认单位为 mA |
| 输入功率 | BL0942 `WATT` | `sys_bl0942.c` -> `ac_powerpa` | 按平台 W 显示口径换算 |
| 输出电压 | MCU ADC CH2 | `sys_Vo_Io.c` -> `Vo_value` | 只有平台要求输出侧时才映射 |
| 输出电流 | MCU ADC CH4 | `sys_Vo_Io.c` -> `Io_value` | 只有平台要求输出侧时才映射 |

不允许做法：

- `EleInfo.v` 用输入电压，`EleInfo.c` 用输出电流，`EleInfo.p` 又用输入功率。
- 采集值未更新时仍直接上报旧值而不做有效性判断。
- 为了让平台有数字显示，填固定电压、电流或功率。

优先级：中。  
复杂度：取决于平台口径。  
阻塞风险：无。

### 3.6 功率和电能单位需要统一

当前代码：

```c
ac_powerpa = get_ac_power(tmp);                  // 0.01W
cJSON_AddItemToArray(p, cJSON_CreateNumber((double)((ac_powerpa + 5U) / 10U)));
```

问题：

- `ac_powerpa` 源变量注释为 0.01W。
- 当前上报 `p` 做 `/10`，结果是 0.1W。
- 中科协议表里 `EleInfo.p` 单位写的是 W。
- 当前分析报告中把 `p` 解释成 0.1W，和协议存在冲突。
- 目前平台显示逻辑是“设备上传多少数字，平台就显示多少 W”。例如设备实际最大约 55.8W，如果上传 `558`，平台会显示 `558W`，这是明显错误。

修复建议：

按当前平台显示口径，应上传整数 W：

```c
p[0] = (ac_powerpa + 50U) / 100U;   // 0.01W -> W，四舍五入
```

示例：

| 实际功率 | `ac_powerpa` 原始值 | 当前错误上传 | 平台错误显示 | 修复后上传 | 平台显示 |
|---|---:|---:|---:|---:|---:|
| 55.8W | 5580 | 558 | 558W | 56 | 56W |
| 77.0W | 7700 | 770 | 770W | 77 | 77W |
| 12.4W | 1240 | 124 | 124W | 12 | 12W |

如果业务要求“不允许显示超过额定最大功率”，可以改用向下取整：

```c
p[0] = ac_powerpa / 100U;            // 55.8W -> 55W
```

推荐默认使用四舍五入，因为平台单位是 W，整数 W 显示允许正常四舍五入；如果审核或客户要求不能超过铭牌，再改为向下取整。

本项目当前已确认平台按原始数字显示 W，因此固件侧不应再保留 `0.1W` 上传口径。后续如果平台显示逻辑发生变化，必须重新同步协议和测试样例，不能在设备端默默切换单位。

电能字段也需要确认：

| 字段 | 当前变量 | 风险 |
|---|---|---|
| `rEc[0]` | `energy_this_time` | 代码注释接近 0.01Wh，协议写 Wh |
| `tEc[0]` | `sys_data.ac_EnergyP` | 注释存在 Wh、0.01Wh 混用 |

建议阶段 1 不先改电能单位，只补充注释和测试样例；阶段 2 根据平台确认结果统一 `p/rEc/tEc`。

优先级：中。  
复杂度：低到中。  
阻塞风险：无。

### 3.7 不支持的硬件字段不应上报

当前代码存在若干固定值字段：

```c
cJSON_AddNumberToObject(per_sts, "lux", 0);
cJSON_AddNumberToObject(signal, "cellid", 0);
cJSON_AddNumberToObject(signal, "pci", 0);
cJSON_AddNumberToObject(signal, "snr", 0);
cJSON_AddNumberToObject(angle, "x", 0);
cJSON_AddNumberToObject(angle, "y", 0);
cJSON_AddNumberToObject(angle, "z", 0);
```

问题：

- 没有光照传感器时，`lux=0` 不代表真实 0 lux。
- 没有倾角传感器时，`Angle.x/y/z=0` 不代表灯杆水平。
- 没有模组 AT 查询结果时，`cellid/pci/snr=0` 不代表真实网络参数。
- 平台看到这些字段，会认为设备真实采集到了这些值，属于伪造数据风险。

修复建议：

| 字段 | 当前情况 | 建议 |
|---|---|---|
| `PerSts.temp` | NTC 支持 | 保留 |
| `PerSts.lux` | 当前未看到真实光照采集源 | 不上报，或平台确认后删除该字段 |
| `Signal.reg` | 可由 `online` 表示连接状态 | 可保留，但含义应写清楚 |
| `Signal.rsrp` | 当前由 `getSignal()` 等级估算 | 建议改为真实 AT 查询；未实现前可不上报或标注为估算 |
| `Signal.cellid/pci/snr` | 当前固定 0 | 不上报，直到接入 `AT+QENG="servingcell"` 等真实解析 |
| `Angle.x/y/z` | 当前无倾角硬件 | 整个 `Angle` 不上报 |
| `EleInfo.e[0]` | Meter 故障状态当前固定 0 | 若没有 BL0942 通信故障检测，不应固定报正常；应接入故障状态或不上报 |

真实获取方式：

- 光照：必须有光敏 ADC、光照传感器或明确外设输入，换算为 lux 后再上报。
- 姿态：必须有倾角传感器、加速度计或外部姿态模块，得到 x/y/z 后再上报。
- 网络小区信息：通过模组 AT 命令读取，例如 `AT+QENG="servingcell"`，解析 cellid、pci、snr、rsrp 后再上报。
- Meter 故障：通过 BL0942 通信超时、校验失败连续计数或状态寄存器判断，不能一直填 0。

周期上报修复建议：

- `CT="C"` 仍保留 `RunTm/LightTm/RunSts/EleInfo/PerSts.temp`。
- 如果没有真实信号详情，只保留可证明的 `Signal.reg`，或暂时不加 `Signal`。
- 如果没有倾角硬件，不调用 `zk_add_angle_group()`。
- 如果 `PerSts` 只有温度真实，则只上报 `temp`，不要带 `lux=0`。

优先级：高。  
复杂度：低。  
阻塞风险：无。

### 阶段 4：低频持久化历史累计时间

目标：

- `RunTm.tTime` 和 `LightTm.tLtTime[0]` 掉电后不归零。
- 不增加高频 Flash 擦写。
- 不破坏 `sys_data_st` 结构体大小。

现状分析：

| 区域 | 地址 | 当前用途 |
|---|---|---|
| `DATAROM_STARTADDR` | `0x08005000` | `sys_data_st` 主区 |
| `DATAROM_STARTADDR + FLASH_PAGE_SIZE` | `0x08005800` | ZK 属性参数主区 |
| `0x08006000` | `0x08006000` | ZK 工作计划主区 |
| `BAKDATAROM_STARTADDR` | `0x08006800` | `sys_data_st` 备份区 |
| `BAKDATAROM_STARTADDR + FLASH_PAGE_SIZE` | `0x08007000` | ZK 属性参数备份区 |
| `0x08007800` | `0x08007800` | ZK 工作计划备份区 |

当前 `0x08005000` 到 `0x08008000` 参数区已经被主备数据、属性、计划占满，不建议再强行新增独立 Flash 页。否则容易压到 `APROM_STARTADDR=0x08008000`，影响 App 分区。

容量核算：

| 页 | 地址 | 页大小 | 当前记录估算 | 剩余空间估算 | 结论 |
|---|---:|---:|---:|---:|---|
| sys_data 主区 | `0x08005000` | 2048B | 408B | 约 1640B | 不建议再塞字段，保持 408B 结构锁定 |
| ZK 属性主区 | `0x08005800` | 2048B | 约 116B | 约 1932B | 可放一条 runtime 小记录 |
| ZK plan 主区 | `0x08006000` | 2048B | 约 652B | 约 1396B | 不占用，避免影响 plan |
| sys_data 备份区 | `0x08006800` | 2048B | 408B | 约 1640B | 不建议再塞字段，保持 408B 结构锁定 |
| ZK 属性备份区 | `0x08007000` | 2048B | 约 116B | 约 1932B | 可放一条 runtime 小记录 |
| ZK plan 备份区 | `0x08007800` | 2048B | 约 652B | 约 1396B | 不占用，避免影响 plan |

runtime 小记录估算约 28B，即使按 32B 对齐计算，放在属性页 `+0x200` 后也只占到页内 `0x220` 左右，距离下一页 `0x08006000/0x08007800` 还很远。因此容量上放得下。

是否影响当前结构：

- 不修改 `sys_data_st`。
- 不新增 `sys_data_st` 字段。
- 不破坏 `SYS_DATA_ST_EXPECTED_SIZE == 408` 的大小约束。
- 不修改 Keil 分区和 scatter。
- 不改工作计划存储页。
- 只在已有 ZK 属性参数页中划出固定偏移保存一条小记录。

推荐持久化位置：

```c
#define ZK_RUNTIME_FLASH_MAIN_ADDR   (ZK_PROPERTY_FLASH_MAIN_ADDR + 0x200U)
#define ZK_RUNTIME_FLASH_BACKUP_ADDR (ZK_PROPERTY_FLASH_BACKUP_ADDR + 0x200U)
```

说明：

- `ZK_PROPERTY_FLASH_MAIN_ADDR` 当前是 `DATAROM_STARTADDR + FLASH_PAGE_SIZE`，即 `0x08005800`。
- `ZK_PROPERTY_FLASH_BACKUP_ADDR` 当前是 `BAKDATAROM_STARTADDR + FLASH_PAGE_SIZE`，即 `0x08007000`。
- `+0x200` 用于避开属性参数记录头部，保留同一页后半段作为运行统计小记录。
- 实现前必须加静态检查，保证属性记录和运行统计记录不会在同一页内重叠。
- 当前 `hw_flash_write_bytes()` 是整页读出、局部更新、整页擦写回写；同页内写 runtime 记录时会保留属性记录，写属性记录时也会保留 runtime 记录。实现时仍必须做写后读回校验。

建议记录字段：


```c
typedef struct
{
    uint32 magic;
    uint16 version;
    uint16 size;
    uint32 seq;
    uint32 total_run_minutes;
    uint32 total_light_minutes;
    uint32 last_saved_boot_minutes;
    uint32 checksum;
} zk_runtime_stats_record_t;
```

字段说明：

| 字段 | 说明 |
|---|---|
| `magic` | 固定魔数，用于判断记录是否有效 |
| `version` | 记录版本，后续字段变化时升级 |
| `size` | 结构体大小，防止旧版本误读 |
| `seq` | 主备选择依据，序号大的为新 |
| `total_run_minutes` | 历史累计运行分钟 |
| `total_light_minutes` | 历史累计亮灯分钟 |
| `last_saved_boot_minutes` | 最近一次保存时本次上电运行分钟，用于调试和重复保存判断 |
| `checksum` | CRC 或校验和 |

RAM 运行变量建议：

```c
static uint32 zk_boot_run_seconds;
static uint32 zk_boot_light_seconds;
static uint32 zk_total_run_base_minutes;
static uint32 zk_total_light_base_minutes;
static uint32 zk_runtime_last_tick;
static uint32 zk_runtime_last_save_tick;
```

上报计算：

```c
RunTm.rTime = zk_boot_run_seconds / 60U;
RunTm.tTime = zk_total_run_base_minutes + RunTm.rTime;

LightTm.rLtTime[0] = zk_boot_light_seconds / 60U;
LightTm.tLtTime[0] = zk_total_light_base_minutes + LightTm.rLtTime[0];
```

保存计算：

```c
record.total_run_minutes =
    zk_total_run_base_minutes + (zk_boot_run_seconds / 60U);

record.total_light_minutes =
    zk_total_light_base_minutes + (zk_boot_light_seconds / 60U);
```

上电加载：

1. 从主区 `ZK_RUNTIME_FLASH_MAIN_ADDR` 读取记录。
2. 从备份区 `ZK_RUNTIME_FLASH_BACKUP_ADDR` 读取记录。
3. 校验 `magic/version/size/checksum`。
4. 主备都有效时选择 `seq` 大的记录。
5. 加载到 `zk_total_run_base_minutes` 和 `zk_total_light_base_minutes`。
6. 本次上电计数 `zk_boot_run_seconds/zk_boot_light_seconds` 从 0 开始。

保存频率建议：

- 生产默认建议每 6 小时或 12 小时保存一次。
- 如果审核阶段需要观察效果，可以临时用 60 分钟保存一次，但不建议作为长期量产策略。
- 只有累计分钟发生变化才保存。
- 掉电检测路径如果时间允许，可保存一次。
- 参数写入、plan 写入、OTA 期间不抢占保存；如果发送/Flash 忙，则跳过本轮，下个周期再保存。

掉电与误差说明：

- 如果按 6 小时保存，异常断电最多丢失最近 6 小时累计；掉电补保存成功时误差会明显降低。
- 如果项目要求更小误差，可以改成 1 小时，但要评估 Flash 擦写寿命。
- 不建议每分钟保存，因为 Flash 擦写次数会快速增加。
- 掉电保存只能作为补充，不能依赖它保证 100% 成功。

Flash 寿命注意：

- 同一页保存一次就会擦写该页一次。
- 如果每 1 小时保存一次，每页一年约 8760 次擦写，接近常见 MCU Flash 擦写寿命量级，不适合作为长期量产默认策略。
- 如果每 6 小时保存一次，每页一年约 1460 次擦写，风险低很多。
- 如果每 12 小时保存一次，每页一年约 730 次擦写，更适合长期运行设备。
- 因此本项目推荐 6 小时或 12 小时保存一次，再配合掉电补保存。

注意：

- 不建议每分钟写 Flash。
- 不建议放进 `sys_data_st`，该结构当前有大小锁定。
- 不建议引入文件系统或复杂日志。
- 不建议使用 `sys_data.couter/day/today_Energy` 等旧字段挤占含义，避免后续维护误判。
- 不建议使用工作计划页 `0x08006000/0x08007800`，避免和 plan 持久化互相覆盖。

实现约束：

- 用主备双副本，和现有属性参数保存风格一致。
- 写入前准备完整 record，写后读回校验。
- 保存函数只尝试一次，不循环等待。
- 保存失败只打印或计数，不阻塞主流程。
- 运行统计在 RAM 中进行，上报只读取 RAM 值。

需要增加的测试：

- `sys_data_st` 大小仍为 408。
- `ZK_RUNTIME_FLASH_MAIN_ADDR` 不等于 `DATAROM_STARTADDR`，不等于 `ZK_PLAN_FLASH_MAIN_ADDR`。
- `ZK_RUNTIME_FLASH_BACKUP_ADDR` 不等于 `BAKDATAROM_STARTADDR`，不等于 `ZK_PLAN_FLASH_BACKUP_ADDR`。
- 属性记录和 runtime 记录在同一页内不重叠。
- 保存间隔不是 1 秒/1 分钟高频写入，量产默认不小于 6 小时。

验收：

- 连续运行 2 小时，重启后 `tTime` 不归零。
- 亮灯 30 分钟后重启，`tLtTime[0]` 不归零。
- 长时间运行 Flash 写入次数可控。
- 修改后 `sys_data_st_size_must_remain_408` 仍能通过编译。

## 6. 不建议做的方案

以下做法不符合当前设备形态，风险较高：

- 为了等最终电流电压，在上报函数里阻塞 3 秒。
- 每次亮灭变化都立即写 Flash。
- 每秒保存运行时间到 Flash。
- 把运行时间字段直接塞进 `sys_data_st` 导致结构体变大。
- 在 `EleInfo` 内混用输入侧电压、输出侧电流、输入侧功率。
- 没有硬件来源时填 `lux=0`、`Angle=0`、`cellid=0`。
- 继续把 55.8W 按 `558` 上传，导致平台显示 `558W`。
- 把变化上报改成高频实时流。
- 为单路 LED 电源引入复杂多路运行统计框架。
- 上电默认满功率通过远程控制处理函数触发，导致多发变化上报。
