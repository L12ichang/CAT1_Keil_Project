# 固件烧录启动登录故障复盘

记录日期：2026-04-18

本文档沉淀本次“烧录后设备功率异常、启动登录异常、怀疑 Bootloader 被覆盖”的完整排查和修复经验。后续遇到类似问题时，优先按本文的分区、参数、启动和登录链路逐项核对。

## 结论

本次问题不是烧录脚本全量擦写导致 Bootloader 丢失。当前烧录流程写入范围是 App 分区 `0x08008000..0x0801B523`，未写 `0x08000000` Bootloader 区。

根因是多个边界条件叠加：

1. App 起始地址改为 `0x08008000` 后，向量表、烧录脚本、Bootloader 跳转流程必须同步。
2. 登录重构引入 JSON 和 MQTT 状态机后，暴露了 cJSON 内存池未 8 字节对齐导致的 HardFault。
3. IMEI 和 ICCID 解析没有严格按长度过滤，15 位 IMEI 曾被错误写入 ICCID，而 MQTT 登录仍使用默认设备号。
4. 运行参数结构体变大，且参数地址一度从旧区 `0x08005000/0x08006800` 改到新区 `0x0801C000/0x0801D800`，导致 App 读不到原设备校准参数，功率输出表现异常。
5. J-Link 普通 reset/go 会让 Bootloader 停在等待循环，这不是 App 崩溃，也不是 Bootloader 被擦除。

当前设备侧已验证：

- App 已烧录并回读校验通过。
- Bootloader 仍存在，且已有备份。
- App 可运行，`VTOR=0x08008000`。
- 设备 IMEI 已使用 `860608074512731`。
- MQTT topic 已使用 `MS/860608074512731/...`。
- 登录状态 RAM 值为 `0x02`，对应 `ZK_LOGIN_STATE_ONLINE`。
- 原工厂校准参数已从旧参数区迁移到当前结构，主区和备份区校验均通过。

仍需现场验证的内容：

- 真实断电上电路径是否符合量产预期，J-Link soft reset 不能替代冷启动验证。
- 平台后台是否记录该 IMEI 的登录、心跳和业务数据。
- 带实际负载时的输出电流、功率、计量值是否符合校准要求。

## 本次修复做了什么

### 1. 烧录流程修复

相关文件：

- `tools/mcu_workflow.py`
- `config/mcu_workflow.json`
- `HK32F103CCT6A.ld`

修复点：

- 所有 ELF/HEX/AXF 先归一化为 BIN。
- 使用 `loadbin {bin},0x08008000`，不再使用容易按 ELF 内部地址写入的 `loadfile`。
- 烧录前计算 `flash_end`，超过 `0x08024000` 立即拒绝，避免覆盖 OTA 备份区。
- 链接脚本固定 App 起始地址为 `0x08008000`。
- 链接脚本限制固件镜像不能覆盖 OTA 备份区。
- 回读验证写入内容和 BIN 内容一致。
- 烧录收尾不再只做 J-Link reset/go，而是在 Bootloader 等待循环中写 RAM `0x20000000=1` 后运行，释放 App。

注意：`0x20000000=1` 只写 SRAM，不写 Flash，不会破坏 Bootloader 或参数区。

### 2. App 向量表和中断修复

相关文件：

- `Core/Src/system_stm32f1xx.c`
- `Core/Startup/startup_stm32f103xe_gcc.S`
- `Core/Src/stm32f1xx_it.c`
- `Core/Src/main.c`
- `Core/Src/hw_uart2.c`
- `Core/Src/hw_uart3.c`

修复点：

- `VECT_TAB_OFFSET` 改为 `0x00008000`，运行时 `VTOR=0x08008000`。
- 启动文件中不再让真实中断处理函数被 weak alias 覆盖。
- 真实 IRQ handler 增加 `used` 和 `externally_visible`，避免链接优化误删。
- `__enable_irq()` 提前到首次 `printf()` 和 `delayMs()` 之前。
- 看门狗初始化推迟到长启动流程之后，避免初始化阶段被复位。
- UART3 DMA 发送完成回调接入 `HAL_UART_TxCpltCallback`。
- `dma_printf()` 避免在中断关闭时永久等待 TX 完成。

这些修复解释了为什么“看起来只改协议层”也会影响功率输出。协议层日志、JSON、4G 初始化大量依赖 DMA 串口、SysTick、中断和看门狗；如果 App 已跳到 `0x08008000`，但中断仍跑到 `0x08000000` 的 Bootloader 向量表，底层 DMA 和定时流程就会异常。

### 3. 登录和 IMEI 修复

相关文件：

- `Core/Src/LampProtocolLib/NbDriver.c`
- `Core/Src/LampProtocolLib/mqtt_zk_protocol.c`
- `Core/Src/LampProtocolLib/mqtt_zk_protocol.h`
- `Core/Src/LampProtocolLib/Json_Protocol.c`

修复点：

- cJSON 静态内存池按 8 字节对齐。
- cJSON 分配器按实际池地址对齐，避免 `double` 字段触发非对齐访问。
- 登录 JSON 使用固定 `snprintf` 构造，降低登录包构造的内存压力。
- IMEI 解析必须精确匹配 15 位数字。
- ICCID 解析要求至少 18 位数字，避免把 15 位 IMEI 当成 ICCID。
- 即使 `AT+CGSN` 回包延迟到后续状态，也会优先捕获 15 位 IMEI。
- 更新 `IMEI`、`IMEI10`、`IMEI_DEC` 和 MQTT 配置中的 `client_id/username/topic`。

验证数据：

```text
IMEI RAM: 860608074512731
MQTT topic: MS/860608074512731/dev2plt
登录状态: 0x02
发送缓存: AT+QMTPUBEX=0,1,1,0,"MS/860608074512731/dev2plt",492
```

### 4. 校准参数和系统参数迁移

相关文件：

- `Core/Src/sys_data.h`
- `Core/Src/sys_data.c`
- `Core/Src/factory_user_data.c`
- `Core/Src/factory_user_data.h`

本次发现：

- 旧参数区 `0x08005000/0x08006800` 有有效工厂参数。
- 新参数区 `0x0801C000/0x0801D800` 读到全 `0xFF`。
- 旧结构体有效长度为 `340` bytes。
- 当前结构体长度为 `408` bytes。
- 按当前结构体直接校验旧参数会失败。

修复点：

- `DATAROM_STARTADDR` 恢复为 `0x08005000`。
- `BAKDATAROM_STARTADDR` 恢复为 `0x08006800`。
- `APROM_SAFE_ENDADDR` 应与 APP 分区上限保持一致为 `0x08024000`，避免 APP 与 OTA 备份区重叠。
- `sys_data_load()` 支持旧 340 字节结构校验。
- 识别旧结构后清零新增字段，调用 `factory_user_load_data()`，再保存为当前 408 字节结构。
- 主区和备份区都会保存迁移后的当前结构。

迁移前关键数据：

```text
旧参数主区: 0x08005000
旧参数备份区: 0x08006800
旧 340 字节校验: 0xCCC8，有效
当前 408 字节校验: 无效，末尾为 0xFFFF
工厂参数 bytes[0x10..0x17]: 06 F4 0A F0 00 32 00 00
```

迁移后关键数据：

```text
主区文件: artifacts/sys_data_after_migration_0x08005000_0x198.bin
备份文件: artifacts/sys_data_bak_after_migration_0x08006800_0x198.bin
当前 408 字节校验: 0xCACA，有效
工厂参数 bytes[0x10..0x17]: 06 F4 0A F0 00 32 00 00
```

按 `factory_user_data.h` 的解释，上述工厂参数解码为：

| 参数 | 字节 | 值 |
| --- | --- | --- |
| `SET_OUTCUR` | `06 F4` | `1780` mA |
| `HWMAX_OUTCUR` | `0A F0` | `2800` mA |
| `OUTPUT_CUR_SENSOR` | `00 32` | `50` mOhm |
| `OP_PWM_OFFSET` | `00 00` | `0` |

这组参数和默认值不同。默认值在代码里是 `SET_OUTCUR=2700`、`HWMAX_OUTCUR=4700`、`OUTPUT_CUR_SENSOR=30`、`OP_PWM_OFFSET=0`。读不到旧校准时，功率和电流控制会明显偏离原设备状态。

## 为什么会出现这次问题

这不是单一 bug，而是重构边界没有一次性收敛。

协议层重构看似只涉及 MQTT、JSON、登录和心跳，但嵌入式系统中这些模块会穿透到底层：

- 登录日志依赖 DMA UART。
- MQTT 状态机依赖 SysTick。
- cJSON 使用 `double` 和结构体对齐。
- App 地址变化依赖 Bootloader、向量表、链接脚本和烧录工具一致。
- 登录新增状态字段改变了 `sys_data_st` 的结构体长度。
- 系统参数区存放校准参数，读取失败会影响电源输出，而不是只影响协议。

所以“协议层改动”最终暴露为功率异常、登录异常和启动异常。

## Bootloader 判断

项目当前不包含 Bootloader 源码，这是工程完整性问题，但不是本次 Bootloader 被擦除的证据。

已确认：

- 设备 Bootloader 可读回。
- 烧录脚本写入范围不覆盖 `0x08000000`。
- J-Link 观察到 Bootloader 等待循环 PC 在 `0x080027xx`。
- App 释放后 PC 进入 `0x0800xxxx`，`VTOR=0x08008000`。

Bootloader 等待循环释放方法：

```text
halt
w1 0x20000000 0x01
go
```

不要在写 `0x20000000` 后再 `reset`，因为 reset 后 Bootloader 会重新初始化 RAM 状态，释放标志可能被覆盖。

另一个 RAM 魔数 `0x20000028=0xAA55AA55` 是 Bootloader 早期路径会检查的值，但本次 J-Link reset 流程下不适合作为最终释放手段。

## 如何判断是否彻底解决

### 已经解决的范围

以下内容已在设备侧闭环验证：

1. App 不再烧到 Bootloader 地址。
2. 烧录后回读校验通过。
3. App 向量表运行在 `0x08008000`。
4. App 可从 Bootloader 等待循环释放运行。
5. 原校准参数已迁移，主备参数区当前结构校验通过。
6. IMEI 使用真实设备值 `860608074512731`。
7. MQTT 登录状态到达 `ZK_LOGIN_STATE_ONLINE`。
8. 登录 topic 使用真实 IMEI。

### 不能宣称已经完全解决的范围

以下内容需要现场或平台配合验证：

1. 真实断电上电后 Bootloader 是否按产品设计自动跳 App。
2. 平台后台是否确认该 IMEI 的登录和心跳。
3. 带实际负载时功率、电流、电压和计量是否符合标定。
4. 长时间运行后是否有看门狗复位、4G 断链重连、心跳超时等问题。

如果这些验证都通过，才能说“整机闭环彻底解决”。当前可以说“代码和设备侧启动登录主链路已经修复并验证通过”。

## 后续避免方法

### 1. 建立 Flash 分区契约

必须维护一份唯一可信的分区表，至少包含：

```text
0x08000000..0x08004FFF  Bootloader
0x08005000..0x080067FF  系统参数主区
0x08006800..0x08007FFF  系统参数备份区
0x08008000..0x08023FFF  App
0x08024000..0x0803FFFF  OTA 备份区
```

后续不允许在多个头文件中随意重复定义地址。至少要在评审中检查：

- 链接脚本地址。
- Bootloader 跳转地址。
- OTA 安全上限。
- 参数读写地址。
- 烧录脚本 base address。

### 2. 烧录必须固定 App 基址

禁止直接对 App ELF 使用不带地址边界检查的全量写法。标准流程：

```bash
./AUTOMATION_SCRIPT.sh build
./AUTOMATION_SCRIPT.sh validate
./AUTOMATION_SCRIPT.sh flash
```

验收点：

- 输出必须包含 `写入范围: 0x08008000..`。
- `flash_end` 必须小于 `0x08024000`。
- 回读校验必须通过。
- 不允许出现 `loadfile` 替代 `loadbin {bin},0x08008000`。

### 3. 每次改 App 起始地址都要同步 VTOR

检查项：

```text
链接脚本 ORIGIN == 0x08008000
g_pfnVectors == 0x08008000
SCB->VTOR == 0x08008000
中断 handler 没有被 weak alias 覆盖
DMA 串口日志不会在中断关闭时阻塞
```

J-Link 快速检查：

```text
halt
regs
mem32 0xE000ED08,1
go
```

### 4. 结构体持久化必须有版本和迁移策略

以后禁止直接扩大持久化结构体后只靠 `sizeof(struct)` 校验旧数据。

建议：

- 在 `sys_data_st` 中增加明确版本号。
- 校验函数同时支持当前版本和最近一个旧版本。
- 新字段必须定义默认值。
- 第一次识别旧版本后迁移并写回当前版本。
- 保留旧参数区的回读样本作为测试输入。

本次旧样本：

```text
artifacts/old_sys_data_0x08005000_0x198.bin
artifacts/sys_data_after_migration_0x08005000_0x198.bin
artifacts/sys_data_bak_after_migration_0x08006800_0x198.bin
```

### 5. IMEI 和 ICCID 必须按协议长度过滤

规则：

- IMEI：精确 15 位数字。
- ICCID：通常 18 到 20 位数字，本项目至少要求 18 位。
- 延迟回包必须允许跨状态捕获。
- 不允许用默认设备号静默登录，除非明确进入测试模式。

验收项：

```text
IMEI RAM == 860608074512731
topic contains MS/860608074512731/
login state == 0x02
```

### 6. JSON 内存池必须对齐

规则：

- cJSON pool 至少 8 字节对齐。
- 自定义 allocator 返回地址也要按 8 字节对齐。
- Cortex-M3 上要关注 `STRD/LDRD` 和 `double` 的非对齐访问。

典型故障特征：

```text
HardFault
CFSR = 0x01000000
UNALIGNED
PC around cJSON_AddNumberToObject
```

### 7. 串口波特率必须使用工程配置

本工程调试串口是 `1000000` baud。使用 `115200` 会看到乱码，不能据此判断设备协议异常。

## 推荐验收清单

每次重构后按顺序执行：

1. `./AUTOMATION_SCRIPT.sh build`
2. `./AUTOMATION_SCRIPT.sh validate`
3. `PYTHONPATH=. python3 tests/test_mcu_workflow.py`
4. `./AUTOMATION_SCRIPT.sh flash`
5. J-Link 读 `PC` 和 `VTOR`。
6. 若停在 Bootloader，写 `0x20000000=1` 后 `go`。

9. 读主备参数区，确认当前结构校验通过。
10. 使用真实负载测试输出功率。
11. 到平台后台确认登录、心跳、上报数据。
12. 做一次真实断电上电测试，不用 J-Link reset 代替。

## 经验教训

1. 只说“协议层重构”不够，嵌入式协议层会依赖中断、DMA、定时器、看门狗、Flash 参数和 Bootloader。
2. App 基址变化是系统级变更，必须同时检查链接脚本、VTOR、烧录、Bootloader 和 OTA。
3. 持久化结构体变更必须有版本和迁移，否则旧设备必然出现参数丢失或默认化。
4. 不要把 J-Link reset 后停在 Bootloader 误判为 App 崩溃。
5. 不要把串口乱码误判为协议异常，先确认波特率。
6. 登录成功不能只看“发出了 MQTT 包”，还要读状态机、IMEI、topic 和平台 ACK。
7. 烧录成功不能只看工具返回成功，还要看写入范围和回读校验。
8. Bootloader 源码缺失是长期风险，至少必须保留二进制备份、哈希和反汇编结论。
9. 校准参数是电源控制的安全边界，任何 Flash 地址迁移都必须先备份并验证。
10. 现场验收必须包含真实断电上电和带载输出测试。
